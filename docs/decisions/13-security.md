# セキュリティ

他のファイルに書かれた安全上の決定（ワークスペースの分離、LLMの接続先の許可リスト、フックの制限、質問ログ、監査ログなど）に加えて、横断的なセキュリティの決定をここにまとめる。特記のないものはM1から適用する。

## 公開の範囲（Q167）

- 管理画面・管理API・配信API・メディアは、すべてインターネットに公開する前提とする。IPアドレスによる制限やVPNの内側への限定は、CMSの機能としては持たない。
- そのため、守りはアプリ側の対策（回数制限、多要素認証、登録済みクエリのみの受付、入口の上限、安全な初期設定など）がすべてを担う。
- 回線そのものをあふれさせる攻撃（L3/L4のDDoS）はアプリでは防げない。その備えはCDNやクラウド側の防御に任せることを手順書に明記する。

## 脅威モデル（Q101）

- **ワークスペースの管理者どうしは互いに信頼しない。** あるワークスペースの管理者が、権限の操作・リセット・招待・資源の消費などを通じて、他のワークスペースのデータや利用者に影響を与えられてはならない。
- 利用者はインスタンス単位で存在し、複数のワークスペースに所属できる。権限の判定では、この「複数の所属」を前提にする。
- サーバー管理者は信頼された運用者とする。ただし、ワークスペースのデータへの操作は、そのワークスペースの監査ログに残す（Q122）。

## ログイン（Q90, Q100, Q104, Q105, Q117, Q118, Q196, Q197）

- **ログインの失敗の制限**（Q105）:
  - アカウント単位では、失敗が続くと次に試せるまでの待ち時間を段階的に延ばす（上限15分程度）。完全なロックにはしない。
  - 前にログインした端末（端末のCookie）からのログインは、端末ごとに同じように数え、アカウントの待ち時間の対象にしない。パスワードを知らない人が失敗を送り続けて本人を締め出せないようにするため（2026-11-09、第三者の確認の R9）。パスワードと多要素認証は省略しない。
  - あわせて、IPアドレス単位でも回数を制限する。
  - 待ち時間中も、応答は待ち時間でないときと区別できないようにする（アカウントの有無を推測させない）。状態コード・本文・ヘッダーをそろえ、応答時間の差も小さくする（待ち時間中もパスワードの照合を行うなど）（Q189）。
- 多要素認証として、TOTP（認証アプリのワンタイムコード）とパスキーに対応する。
- サーバー管理者とワークスペースの管理者は、多要素認証を設定しないと管理操作ができない。
- **全員への多要素認証の必須**（Q197）: インスタンスの設定「全員に多要素認証を必須にする」を設け、**既定で有効**にする。サーバー管理者は無効にできる。
  - 有効なとき、多要素認証を設定していない利用者は、多要素認証の設定に必要な操作（本人の情報の確認、多要素認証の設定、再認証、ログアウト）しかできない。初めてログインした人には、他の操作より先にTOTPの設定を求める。
  - 無効なときは、管理者以外のロールは任意とする。ワークスペース単位の「全員に必須」は設けない（Q118 を 2026-11-09 に変更。全員への必須が既定で有効なため）。
- 外部のOIDC/SSOでログインする利用者は、多要素認証をそちらに任せる。ただし、サーバー管理者とワークスペースの管理者は、SSOでもCMS側のパスキーを必須とし、再認証もパスキーで行う（Q131）。
- 多要素認証には、一度だけ使える復旧コードを発行する。
- **パスワードの強さ**（Q170, Q196）:
  - 最低12文字とする。記号の混在や定期的な変更は強制しない。
  - 単純なパターンのパスワードは、登録・変更のときにコードで拒否する: 同じ文字の繰り返し、連続した文字や数字（`123456789012`、`abcdefghijkl` など）、キーボードの並び（`qwertyuiop12`、`1qaz2wsx3edc` など）、メールアドレスやサイト名を含むもの。
  - よく使われるパスワードの一覧はCMSに同梱しない（Q196。Q178は取り下げ）。漏えいしたパスワードの照合は、次の照会と、全員への多要素認証の必須（Q197）に任せる。
  - Have I Been Pwned への照会（パスワードのハッシュの先頭5文字だけを送るk-匿名性の方式）を、サーバー管理者が設定で有効にできる。既定はOFFとし、初期設定の画面で有効化を推奨する。外部への送信の共通の仕組みを通す。照会先に届かないときは、登録を止めずに長さとパターンの検査だけで通す。
- パスワードを忘れたとき:
  - SMTPを設定していれば、メールでリセットできる。
  - 管理者は他の利用者のリセットを発行できる。**ただし、ワークスペースの管理者が発行できるのは、自分が管理者であるワークスペースにしか所属していない利用者だけ。** それ以外の利用者はサーバー管理者だけが発行できる。管理者が新しいパスワードを直接設定する操作は作らず、本人向けのリンクを発行するだけとする。多要素認証のリセットも同じ範囲とする。発行は監査ログに記録する（Q117）。
  - SMTPを設定していないときは、リセットを発行できるのはサーバー管理者だけとする。リンクは発行した人に渡り、受け取った人は対象の人になりすませるため（2026-11-10、侵入テストの前の確認。招待の Q194 と同じ扱い）。
  - シングルサインオンだけでログインする（パスワードを持たない）利用者には、本人の要求でもワークスペースの管理者からも、パスワードのリセットを発行しない。IdP から外された人が、メールを読めるだけでパスワードのログインを得ないようにするため。回復は IdP で行い、必要ならサーバー管理者が発行する（2026-11-10）。
  - サーバー管理者自身は、サーバー上でCLIを実行して復旧する。ネットワーク越しには復旧できない。
- **リセットと招待のリンク**（Q104）:
  - リンクは、設定にある公開URLだけから作る。リクエストのHostヘッダーは使わない。
  - トークンはランダムで、一度だけ使え、短命（30分程度）とする。DBにはハッシュだけを保存する。
  - リセットしたら、その利用者のセッションをすべて失効させる。
  - リセットの要求への応答は、メールアドレスが登録されているかどうかで変えない。
  - 招待のリンクは、SMTPを設定していればメールで送り、画面には出さない。設定していなければ、招待した人の画面に一度だけ表示し、その人が本人に渡す（Q193）。ただし、SMTPを設定していないときに招待できるのはサーバー管理者だけとする。ワークスペースの管理者がリンクを受け取ると、自分で承諾を試して他のワークスペースの利用者の存在を知れてしまうため（Q194）。

## OIDC/SSO（Q103, Q126）

- M1から提供する。M1の中では、パスワード・多要素認証・セッションを先に完成させ、OIDCは最後に入れる。
- 社内のIdPにつなぐ場合、OIDCの設定の取得も外部への送信の共通の仕組みを通るため、内部宛先の例外の設定が必要になる。手順書に明記する。

- `state`、`nonce`、PKCE、IDトークンの `iss` と `aud` を、実績のあるライブラリで検証する。
- ログインの途中だけで使う短命のCookie（`state` などを保持する）は SameSite=Lax とする。IdPからのリダイレクトで送られる必要があるため。セッションのCookieは Strict のまま。
- JIT（ドメインのルールによる自動作成）は、IDトークンの `email_verified` が真で、かつドメインが一致するときだけ行う。
- メールアドレスが同じというだけで、既存のアカウントに自動でひも付けない。ひも付けは、招待を受けたときか、ログイン中の本人の操作でだけ行う。
- 再認証は、IdPでの再ログイン（`prompt=login` や `max_age`）か、パスキーで行う（Q108）。管理者はパスキーだけで再認証する（Q131）。例外として、SSOの利用者がTOTPを設定済みでパスキーがないときは、パスキーの登録の前にTOTPか復旧コードで確かめる（2026-11-09、第三者の確認）。この確認だけでは、パスキーを求める管理操作は通らない。

## セッション（Q91, Q107, Q108, Q110, Q114）

- 管理画面はCookieのセッションを使う。HttpOnly、Secure、SameSite=Strict を付け、Cookieの名前に `__Host-` の接頭辞を付ける。トークンをlocalStorageに保存しない。
- ログインしたらセッションIDを新しくする。パスワードや多要素認証を変更したら、他のセッションをすべて失効させる（Q107）。
- 無操作の期限と、絶対的な期限（ログインからの最大時間）の両方を設ける。既定は、ログインから12時間、無操作2時間、再認証の有効時間10分とし、設定で変えられる（Q195）。
- 権限（ロールや所属）はリクエストのたびに現在の状態と照合し、セッションに保存した値を信用しない。
- セッションIDは、DBにはハッシュで保存する。
- 状態を変える操作には、CSRFトークンを要求する。
- **管理画面の応答のセキュリティヘッダー**（Q114）:
  - CSPは `script-src 'self'` とハッシュだけを許し、`unsafe-inline` と `unsafe-eval` を使わない。`frame-ancestors 'none'` を付ける。
  - 管理画面のコードでは `v-html` を使わない。リンターで禁止する。
  - 即時通信路（WebSocketなど、M2）は、接続時にOriginを確認する。
- 重い操作（APIキーの発行、LLMの接続設定や予算の変更、権限の変更、質問ログの閲覧、デプロイのトークンの発行など）の前に再認証を求める。**多要素認証を設定した人は、多要素認証で再認証する。** パスワードだけでは通さない。多要素認証を設定していない人はパスワードで再認証する（Q108）。
- 利用者は自分のログイン中のセッションを一覧で見て、失効させられる。
- **CLI**は、利用者が管理画面で発行する個人用のトークンを使う。トークンには有効期限と権限の範囲を付け、発行と失効は監査ログに記録する（Q119）:
  - 有効な権限は、トークンの範囲とリクエストの時点での本人のロールの重なりだけ。トークンが本人の権限を超えることはない。
  - 発行時に、使えるワークスペースを選ぶ。
  - 本人がワークスペースから外されたり、無効にされたりしたら、直ちに使えなくなる。
  - デプロイの範囲は、サーバー管理者だけが付けられる。
- **キーとトークンの渡し方**（Q110）:
  - 配信APIのキーと個人トークンは、`Authorization` ヘッダーでだけ受け付ける。URLのクエリに含まれていたら拒否する。
  - Bearerトークンの経路ではCookieを読まない。Cookieの経路では必ずCSRFトークンを要求する。
  - 管理APIと配信APIは、別のドメインからのアクセスを許すCORSのヘッダーを返さない。

## デプロイ（Q102）

- スキーマ（テンプレート）のデプロイは、サーバー管理者だけが行える。デプロイ専用の範囲を持つトークンを使う。このトークンはほかの範囲と混ぜられず、有効期限は最長30日で、発行のときに多要素認証での再認証を求める。デプロイの実行のときには再認証を求めない（2026-11-09 に変更。CIから使うため）。M2からはマニフェストにJSが入るため、デプロイの権限はサーバー上でコードを動かす権限と同じになる。
- CLIで行う検査（識別子の検証、破壊的な変更の拒否、登録済みのPersisted Queriesの検証、変換関数の必須化など）は、**すべてサーバーでもやり直す**。CLIの検査は、早く知らせるためのものとする。
- デプロイの拒否に関わる約束のテストは、CLIを通さず、APIを直接呼んで確かめる。
- **同梱のテンプレート**（2026-11-11、持ち主の判断。M5 の例外）: リリースに同梱した見本のテンプレート（`templates/blog`）だけは、サーバー管理者の管理画面からもデプロイできる。サーバー管理者のセッションで、多要素認証を設定済みで、デプロイの直前に多要素認証で再認証したときだけ受け付ける（トークンの経路と違い、画面からの操作なので再認証を求める）。デプロイできるのはサーバーのバイナリに埋め込んだ中身だけで、画面から任意のマニフェストや JS は送れない。検査（破壊的な変更、登録済みのクエリ）はトークンの経路と同じに行う。
  - 埋め込む中身は、`templates/<名前>` を CLI の `yomi schema build` でまとめた JSON（`server/bundled-templates/<名前>.json`）。ロックファイルと同じく生成したものとして扱い、CI とローカルの検査で `templates/` から作り直した結果と一致することを確かめる（情報源は `templates/` の1か所のまま。原則2）。

## SQLとワークスペースの分離（Q92, Q111, Q120）

- テーブル名・列名・スキーマ名などの識別子は、利用者の入力から直接作らない。マニフェストの検証を通った名前（英小文字・数字・アンダースコアのみ、長さ制限あり）から内部用の名前を生成する。検証はサーバーで行う（Q102）。
- 識別子のSQLへの埋め込みは、必ず1つの関数を通してクォートする。値は必ずパラメータとして渡す。
- 各リクエストは、トランザクションの中で対象のワークスペースのスキーマだけに切り替える。
- **DBのロールでも分ける**:
  - ワークスペースごとにDBのロールを作り、そのワークスペースのスキーマにだけ権限を持たせる。サーバーはリクエストごとに、トランザクションの中でそのロールに切り替える。
  - 埋め込み、Webhookの送信、夜間の再計算などのジョブも、同じようにワークスペースのロールに切り替えて動かす。
  - ワークスペースのロールは、共通のテーブル（利用者、セッション、キー、監査ログなど）に触れられない。
  - ワークスペースのロールには `statement_timeout` を設定する（Q120）。
  - 普段の処理用のロールは、テーブルの作成・変更・削除（DDL）ができない。移行のときだけ別のロールを使う。
  - 移行（DDL）とワークスペースのDBロールの作成には、普段とは別の設定の専用の接続先を使う。スーパーユーザーは不可で、`CREATEROLE` とDDLの権限を持つ。デプロイとワークスペースの作成・削除のときだけ使う（Q173。削除は2026-11-12に追加）。
  - この接続は動いているサーバーが常に持つことになる（管理画面からのワークスペースの作成、CLIからのデプロイを受け付けるため）。そのため、PostgreSQL 16以上を必須とし（15以前の `CREATEROLE` はほぼスーパーユーザーと同じ操作ができる）、この接続は1本だけの専用の接続にして、ワークスペースの作成・削除とデプロイ（テンプレートの切り替えを含む）の処理以外のコードからは使えない作りにする（Q179。削除は2026-11-12に追加）。
  - 監査ログのテーブルは、普段の処理用のロールからUPDATEとDELETEの権限を取り上げる。保存期間を過ぎたものの削除は、専用のロールだけが行う。
- **DBのロールの限界**: ロールを切り替える権限は、接続に使うロールが持っている。そのため、SQLインジェクションがあれば別のワークスペースのロールに切り替えられる。DBのロールが防ぐのは「スキーマの切り替え忘れ」などの不具合で、SQLインジェクションではない。SQLインジェクションは、値のパラメータ化と識別子の関数で防ぐ。

## 鍵の管理（Q93, Q109）

- CMSが発行して照合するものは、発行時に一度だけ表示し、DBにはハッシュだけを保存する: 配信APIキー、CLI用の個人トークン、多要素認証の復旧コード、リセット・招待のトークン、セッションID。
- CMSが元の値を使うために保管するものは、暗号化してDBに保存する: LLMのAPIキー、Webhookの署名用の秘密、TOTPの秘密。
- 暗号化は認証付き暗号（AEAD）で行い、用途と持ち主のID（ワークスペースID、または Webhook や書き出し先の行のID）を付加データとして結びつける。暗号文を別の行や別のワークスペースに移しても復号できないようにする。
- 秘密やハッシュの照合は、一定時間の比較で行う。
- 暗号化の鍵は、環境変数かファイルで渡し、DBやバックアップには含めない。鍵がなければサーバーは起動しない。
- 暗号化の鍵にはバージョンを付け、新しい鍵を追加して再暗号化し、古い鍵を外せるようにする。
- 発行するキーには、ひと目でわかる接頭辞（例: `yomi_live_`）を付け、秘密の検出の仕組みに引っかかるようにする。キーには任意で有効期限を付けられる。
- 暗号処理（ハッシュ、署名、暗号化）は自作せず、実績のあるライブラリを使う。

## GraphQL（Q94, Q115）

- 本番の配信APIは、**登録済みのクエリだけ**を受け付ける。登録されたクエリのIDによるリクエストだけを実行し、自由に書いたクエリは拒否する。
- クエリの登録は、サイトのビルド時またはデプロイ時にCLIが行う（SSRのサイトも、閲覧のたびではなくデプロイ時に登録する）。登録には、読み取り用とは別の権限のキーを使う。登録時に、クエリの深さと複雑さを検査し、上限を超えるものは登録を拒否する。上限は設定で変えられ、既定値は少なくとも深さ25・別名1000個のクエリを拒否する大きさにする（Q186）。
- 開発モードでは任意のクエリを受け付ける。開発モードはサーバーの設定でインスタンス単位にだけ切り替えられ、ワークスペースごとには切り替えられない。
- 一覧を返すフィールドには、1回に取得できる件数の上限をスキーマで設ける。変数で上限を超える件数を指定しても、上限までしか返さない。
- 本番では、イントロスペクションと、1回のリクエストで複数のクエリを送る機能（バッチ）を無効にする。エラーには内部の詳細（SQL、スタックトレース、内部の名前）を含めない。
- APIキーごとの回数制限と、応答の大きさの上限を設ける。回数制限の既定値は、キーの用途（ビルド用、サーバー配信用）ごとに分ける。用途は発行時に選ぶ、スコープとは別の属性で、回数制限の既定値だけに影響し、権限は変えない（Q153）。サーバー配信用（SSRなど）は閲覧数に応じた問い合わせを受けるため、既定値を大きめにし、上限に近づいたら管理画面で知らせる（Q145）。
- **キャッシュとワークスペースの分離**（Q125）:
  - 配信APIのURLにはワークスペースIDを含める（例: `/ws/<ワークスペースID>/graphql`）。サーバーは、APIキーがURLのワークスペースのものかを必ず照合し、一致しなければ拒否する。CDNのキャッシュがURLだけで見分けても、ワークスペースをまたいで応答が混ざらないようにするため。
  - 応答は既定で `Cache-Control: private` とし、共有キャッシュに載せない。
  - 共有キャッシュは、サーバー管理者が明示的に有効にした場合だけ許す。対象は、**公開版の読み取りだけ**を範囲とするキーで実行した登録済みのクエリの応答に限る。
  - 共有キャッシュに載った応答は、CDNがCMSに問い合わせずに返すため、**APIキーの照合なしに、URLを知っている人なら誰でも取得できる**。有効にする画面でこのことを明示する。
  - 共有キャッシュを有効にした場合は、`s-maxage` を短くし、記事の公開状態が変わったらキャッシュの削除用のWebhookを送る。CDNに残った応答はCMSの外にあるため、非公開化の即時性（INV-PUB-02）はCMSの応答についての約束とし、このことを有効にする画面に明示する（Q141）。版の本文を抹消したときも、同じ削除用のWebhookを送る（Q144）。削除の合図には記事の状態変化のWebhook（`01-architecture.md`）を使い、共有キャッシュの有無にかかわらず送る（Q146）。

## 外部への送信（Q95, Q112）

- **外部へのHTTPの送信は、1つの共通の仕組みを通す。** Webhook、監査ログのWebhookへの書き出し（Q81）、フックからの通信（M2）、LLMの呼び出し（M3以降）、OIDCの設定の取得のすべてが、この仕組みを使う。
- 送信先は原則HTTPSに限る。
- 名前解決した後のIPアドレスが内部向けなら送らない。内部向けには、プライベートアドレス、ループバック、リンクローカル、クラウドのメタデータサーバー、`0.0.0.0`、IPv4を埋め込んだIPv6アドレスなどを含める。
- **検査したIPアドレスに固定して接続する。** 検査の後に名前解決をやり直さない（DNSリバインディング対策）。送信のたびに名前解決と検査を行う。
- リダイレクトはたどらない。
- プロキシの環境変数（`HTTP_PROXY` など）は使わない。
- **出口のプロキシ**（Q128）: 社内プロキシを通さないと外部に出られない環境のために、サーバー管理者がCMSの設定でプロキシを明示的に指定できる。
  - 送信の前に、CMSが宛先を名前解決して内部向けでないことを検査する（プロキシがない場合と同じ）。
  - 既定では、HTTPSの中継の依頼（CONNECT）の宛先に、**CMSが検査したIPアドレス**を指定する。TLSの証明書の確認は本来のホスト名で行う。これで、プロキシ経由でも「検査したIPアドレスに固定する」保証を保つ。
  - ホスト名でしか中継を許さないプロキシのために、サーバー管理者は警告を確認したうえで、ホスト名で中継を依頼する方式に切り替えられる。この場合、検査の後に名前解決の結果が変わる攻撃を防げるかはプロキシ次第になることを、設定画面と手順書に明記する。送信前の検査は引き続き行う。
  - プロキシの認証情報は、他の秘密と同じく認証付き暗号で暗号化して保存する（Q109）。
  - プロキシ経由の送信にも、リダイレクトをたどらない、応答の本文を画面に出さないなど、この節の他の規則をすべて適用する。
- サーバー管理者は、自前のビルドサーバーやローカルのLLMなど、必要な内部宛先だけを例外として許可できる。例外には、HTTP（HTTPSでない）での送信の許可も含められる（擬似LLMやOllamaなど）（Q139）。例外はポートまで指定でき、サーバー管理者が設定した宛先（LLMなど）の例外と、ワークスペースの管理者が決める宛先（Webhookなど）の例外を分ける（2026-11-09、第三者の確認の R11）。
- 管理画面のテスト送信などでは、相手の応答の本文を表示しない。ステータスコードだけを表示する。
- **Webhookの署名**:
  - 署名には送信時刻とイベントIDを含め、受け手が古いものや同じものの再送を拒否できるようにする。
  - 署名用の秘密を入れ替えるときは、一定期間、新旧の両方で署名する。
  - 署名はHMAC-SHA256とし、署名の対象（送信時刻・イベントID・本文の結び方）と書式を手順書で公開する（Q188）。

## メディア（Q96, Q113）

- ファイルの中身（先頭のバイト列）で種類を判定し、許可した形式（JPEG、PNG、WebP、GIF）だけを受け付ける。
- **AVIFは受け付けない**（Q127）。2026年10月時点で、Rustだけで書かれ、ライセンスがApache-2.0と両立し、実績のあるAVIFのデコーダーがないため。imageクレートがRustだけでのAVIFのデコードに正式に対応した時点で再検討する。
- 画素数と、デコードにかける時間に上限を設ける。上限を超える画像は拒否する（解凍爆弾の対策）。デコーダーには、Rustだけで書かれた実績のあるライブラリを使う。
- 受け付けた画像は、すべてエンコードし直して保存する。これで写真の位置情報（EXIF）や色の情報（ICCプロファイル。任意のバイト列を入れられるため。第三者の確認の R25）などのメタデータを取り除き、画像とスクリプトを兼ねるファイルも無害化する。位置情報は既定で削除する。
- SVGは既定で受け付けない。サーバー管理者が有効にした場合だけ、無害化してから受け付ける。
- ファイル名は保存時にランダムな名前に置き換え、利用者が指定したパスは使わない。Markdownの取り込みにも適用する。
- ワークスペースごとに、ファイルの大きさと容量の上限を設ける。
- メディアの応答には、スクリプトの実行を禁じるヘッダー（CSPのsandbox、`X-Content-Type-Options: nosniff`）を必ず付ける。
- メディアは、管理画面とは別のドメイン（例: `media.example.com`）から配信することを推奨の設定とする。設定がない場合も、上のヘッダーで守る。
- 下書きや非公開の記事で使っているメディアも、URLを知っていれば取得できる。名前がランダムで推測できないため、これを受け入れる。管理画面と手順書にこのことを明記する。メディアを削除したら、ファイルも削除する。

## 本文（Q97）

- **保存時**（Rustの検証）:
  - リンクの `href` は、`https`、`http`、`mailto`、`tel`、相対パス、`#` で始まるアンカーだけを受け付ける。`javascript:` などは拒否する。
  - 生のHTMLを書けるノードは用意しない。
  - 動画や外部の投稿の埋め込みは専用のノードとし、許可した提供元のURLだけを受け付ける。
- **出力時**（変換器）: HTMLに変換するときは、すべての文字列を必ずエスケープする。カスタムノードの変換関数がHTMLを返す場合は、無害化の処理を通す。
- **ライブプレビュー**: 管理画面とプレビューのページとのやり取り（postMessage）では、相手のドメインを必ず確認する（M2）。

## チャットボットへの悪用（Q98, Q116, M4）

- 質問文の長さに上限を設ける。CMS側でもAPIキーごとの回数制限をかける。
- 中継サーバーから、訪問者ごとの識別子（ハッシュ化したもの）を任意で受け取れるようにし、訪問者単位の回数制限をかける。CMSからは中継のAPIキー1つにしか見えないため、1人の訪問者による予算の食いつぶしを防ぐ。
- プロンプトでは、訪問者の質問と記事の断片を明確に区切り、どちらも指示ではなくデータとして扱うようLLMに伝える（これは保証ではない）。
- **回答に含まれるURLは、根拠にした記事の本文に実際に書かれているURLか、出典と同じサイトのURLだけを残す。** それ以外は取り除くか、リンクにしない。リンクだけでなく、画像のURLにも適用する。
- 回答はMarkdownで返すことを仕様として明記する。公式SDKは、表示する前にエスケープする。
- **外部のLLMに送る前のマスク**（Q169）: 訪問者の質問文は、LLMへの送信と埋め込みの作成の前に、質問ログ（Q20）と同じ規則（メールアドレス、電話番号などの定型パターン、IPアドレス（IPv4・IPv6。2026-10-30に追加））でマスクする。ワークスペースが決める「拒否する語」は `09-qa-chatbot.md` にある。
- LLMの接続設定とチャットボットの有効化の画面に、「訪問者の質問文は（マスクした上で）外部のLLMの提供会社に送られます」と、マスクの限界（氏名や住所などの自由な書き方は残る）を表示する。手順書では、機密性の高いサイトにはローカルのLLMを推奨する。
- 回答の長さに上限を設ける。

## 依存ライブラリと配布物（Q99, Q123）

- **M1から**:
  - CIで脆弱性を検査する（Rustは `cargo audit` / `cargo deny`、Node.jsは `npm audit` 相当）。既知の脆弱性があれば失敗させる。
  - `cargo deny` で、Apache-2.0と両立しないライセンスと、公式以外の取得元を拒否する。
  - ロックファイルを必ずコミットし、依存の更新は自動の更新提案（Dependabotなど）で行う。
  - 依存の追加には持ち主の承認を必須にする（`Cargo.toml` と `package.json` をCODEOWNERSの対象にする）。
  - GitHub Actionsの外部アクションは、コミットのSHAで固定する。
  - ワークフローに与える権限は最小にする（既定は `contents: read`）。
  - npmのインストールでは、パッケージのスクリプトを実行しない（`ignore-scripts`）。
  - 外部からのプルリクエストでは、秘密を使うジョブを動かさない。
- **v1.0の公開までに**:
  - 配布するコンテナイメージとバイナリに署名し、SBOMを付ける。署名は、OIDCによる鍵なしの署名で行う。
  - `SECURITY.md` を置き、非公開の脆弱性報告の窓口と、セキュリティ修正を出すバージョンの方針を示す。

## 運用（Q100, Q106, Q120）

- **ログ**: パスワード、トークン、APIキー、Cookie、記事の本文、質問文をログに出さない（書かないのが第一の決まり）。ログ出力の共通部分では、決まった名前のフィールドの値と、既知の形（CMSのキーとトークン、`Bearer`、接続文字列のパスワード、セッションのCookie）を伏せる。文の中の自由な文は見分けられない（2026-11-09、第三者の確認の R37）。
- **HTTPS**: 本番ではリバースプロキシなどの後ろでHTTPSで動かす前提とし、HSTSヘッダーを付ける。HTTPS前提の設定がないまま本番の設定で起動しようとしたら、起動を止める（Q168でQ100の「警告」を改めた）。
- **安全な初期設定**（Q168）:
  - 公式のDocker Composeでは、PostgreSQLをコンテナの内部ネットワークだけにつなぎ、外にポートを開けない。
  - 秘密の値（DBのパスワード、暗号化の鍵など）は初期値を持たせず、初期化のコマンド（サーバーのバイナリのサブコマンド。例: `yomi-server init`）で生成する。サーバーの起動では生成しない。暗号化の鍵はDBとは別のファイルに書き出し、「DBのバックアップとは別に保管してください」と表示する。鍵がなければサーバーは起動しない（Q93, Q172）。
  - 本番の設定で起動するとき、次のどれかに当てはまれば、理由を表示して起動を止める: 秘密の値が空・短すぎる・既知の初期値（`password`、`changeme` など）である、DBの接続に使うユーザー（普段の接続、移行・ロールの作成用の接続のどちらか）がスーパーユーザーである（Q173）、PostgreSQLが16より古い（Q179）、開発モード（Q115）が有効である、HTTPS前提の設定がない。
  - 開発環境では、同じ検査を警告にとどめる。
- **接続元のIPアドレス**（Q106）: `X-Forwarded-For` などは、設定で信頼すると指定したプロキシから届いた場合だけ使う。
- **入口の上限**（Q106）: リクエストの本文の大きさ、ヘッダーの大きさ、処理時間の上限を、リバースプロキシとは別にサーバー自身でも設ける。
- **ワークスペースごとの上限**（Q120）:
  - 配信API・管理APIの回数制限、メディアの容量、記事数などに上限を設定でき、1つのワークスペースがインスタンス全体の資源を使い切れないようにする。
  - 上限は、初めから有効な既定値を持つ。設定しなければ無制限、にはしない。
  - ジョブの同時実行数を、ワークスペースごとに制限する。
  - 回数制限の数え方とキャッシュのキーには、必ずワークスペースIDを含める。
- **バックアップ**: 公式の手順書に、暗号化の鍵をDBのバックアップと別の場所に保管すること、バックアップ自体も暗号化すること、書き換えや削除ができない保管（オフラインや変更できないストレージ）を併用すること（ランサムウェア対策、Q171）を明記する。版の本文を抹消しても、それ以前のバックアップには残ることを明記し、バックアップの保存期間を決めるよう案内する（Q152）。
- **第三者の視点での確認**: M1の実装を始める前と、v1.0の公開前の2回、設計の議論を見ていない別のAIに、攻撃者の視点で設計とコードを確認させる。指摘への対応は持ち主が判断する。M1前の回は実施済み（`docs/history/2026-10-09-security-review.md`）。

## 検知と事故への備え（Q171）

- **本人への通知**: 新しい端末や場所からのログイン、パスワードや多要素認証の変更、APIキーや個人トークンの発行があったら、本人にメールで知らせる（SMTPを設定している場合）。
  - 通知は、利用者ごとに設定する言語（日本語・英語）だけで送る。利用者が設定していなければ、インスタンスの既定の言語（設定で変えられる。初期値は英語）で送る。まだ利用者でない宛先への招待のメールも、インスタンスの既定の言語で送る（Q198）。
  - SMTPへの接続は、STARTTLS（既定）か TLS で行う。暗号化しない接続は、同じホストの中継（ループバックの宛先）にだけ許し、本番の設定でそれ以外を指定したら起動しない（Q199）。
  - DBへの接続も同じ考え方とする。ループバックの外のDBで、接続のURLに `sslmode` がない（`prefer`）か `allow` なら、TLSが使えないときに黙って平文に落ちるので、本番の設定では起動しない。`require` 以上か、信頼できる閉じたネットワークで意図して平文を選ぶ `disable` を書かせる。公式の Docker Compose は `disable` を書く（2026-11-10）。
  - 新しい端末は、ログインに成功した端末に置く長期のCookie（ランダムなID、DBにはハッシュで保存）で判定する。Cookieは `__Host-`・HttpOnly・Secure・SameSite=Strictとし、新しい端末の通知と、ログインの失敗を端末ごとに数えること（「ログインの失敗の制限」）に使う。このCookieがあっても多要素認証は省略しない（Q181）。
  - 場所は、サーバー管理者がGeoIPのデータを用意した場合だけ、国の変化として判定する。GeoIPのデータは同梱しない（Q175）。
  - ログインの履歴（IPアドレス、ブラウザの種類、国）は90日で自動削除する。期間は設定で変えられる（Q176）。
- **管理者への通知**（M2、Q174）: ログイン失敗の急増、回数制限への到達の急増、多要素認証のリセット、サーバー管理者の権限の付与などを、監査ログの外部への書き出し（Q81）と同じ経路で知らせる。インスタンス単位の事象（ログイン失敗の急増など）はサーバー管理者だけに知らせ、ワークスペースの管理者には自分のワークスペースの事象だけを知らせる。通知の本文には、パスワードやトークンなどの秘密の値を含めない。通知は監査ログの記録に「知らせる」印を付けたもので、書き出し先に加えて管理画面にも出す（ワークスペースの通知はそのワークスペースの管理者の「やること」、インスタンス単位の通知はサーバー管理者の画面。1人ずつ「確認した」にできる）。急増の通知には、件数の多いIPアドレス・利用者のID・メールアドレス（存在するアカウントのものだけ）を含める（`11-permissions-and-audit.md`、M2の計画の15番）。
- **緊急停止の操作**: サーバー上のCLI（サーバーのバイナリのサブコマンド。本番にはNodeがないため、開発用のNode製のCLIとは別。Q180）で、次を実行できるようにする。ネットワーク越しの管理APIからは実行できない。実行は監査ログに記録する。
  - すべてのセッションと個人トークンの一斉失効。あわせて、未使用のリセットのトークン、未承諾の招待、すべてのワークスペースのプレビュー用トークンも失効させる（2026-11-10、出回っているかもしれないものをまとめて止めるため）
  - すべての配信APIキーの入れ替え
  - 暗号化の鍵の入れ替え（Q93）
- **事故対応の手順書**: 何を止め、何を入れ替え、誰に知らせるかの手順を公式の手順書に載せる。日本の個人情報保護法では一定の漏えいについて個人情報保護委員会への報告と本人への通知が義務になることを案内する。
- **侵入テスト**: v1.0の公開前に、動いている実物に対する第三者の侵入テストを行う（設計の確認だけでは実装のバグは見つからないため）。
