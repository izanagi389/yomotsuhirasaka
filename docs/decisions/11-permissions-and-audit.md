# 権限と監査ログ

## ロールと権限（Q76）

固定のロールはM1、重い権限の個別付与とレビュー依頼はM2（Q88）。

- 基本は固定のロールとする。

| ロール | 主な権限 |
|---|---|
| 管理者 | ワークスペースのすべての操作、重い権限の付与 |
| 編集者 | 記事の作成・編集・公開、訂正としての公開、確認済みの記録、レビュー |
| 執筆者 | 記事の作成・編集、レビューの依頼、原文の更新の反映済みの記録（Q164）。公開はできない（Q77） |
| 閲覧者 | 閲覧のみ |

- 重い権限だけは、個人に追加で付与できる。
  - 質問ログの閲覧（**どのロールにも既定では付けず、管理者だけが付与できる**）
  - LLMの接続設定と予算の変更
  - 学習への利用の拒否など、サイトの方針に関わるスイッチ
  - 訂正としての公開、確認済みの記録
  - 編集の引き継ぎ
  - テンプレートの切り替え（2026-11-11。**どのロールにも既定では付けず、付与できるのはサーバー管理者だけ**。切り替えはスキーマとフックの JS を変え、データを消しうるため。`02-schema-and-delivery-api.md`「テンプレートの切り替え」）
- 細かい権限を自由に組み合わせてロールを作る仕組みは作らない。
- 上の表で確定する（Q192）。あわせて、次のとおりとする。
  - 執筆者は、他の人が書いた記事も編集できる。
  - 編集者は、記事を削除できる。執筆者は削除できない（削除できるのは管理者と編集者だけ。Q200）。
  - 閲覧者は、下書きも見られる。

## ワークスペースと利用者（Q101, Q117, Q121）

ワークスペースの管理者どうしは互いに信頼しない（`13-security.md` の脅威モデル）。利用者はインスタンス単位で存在し、複数のワークスペースに所属できる。

- ワークスペースの作成は、サーバー管理者だけができる。組織の層を入れた後は、組織の管理者も、自分の組織の中に作れる（2026-11-25、下記「組織」。INV-TEN-06 は組織の層の実装のときに改める）。
- ワークスペースの削除も、サーバー管理者だけが管理画面から行える（2026-11-12、M5 の例外）。組織の層を入れた後は、組織の管理者も、自分の組織のワークスペースを同じ手順で削除できる（2026-11-25。INV-TEN-07 は組織の層の実装のときに改める）。
  - 削除には、ワークスペースの名前の入力と、直前の本人の確認（再認証）を求める。個人トークンでは行えない。
  - 削除はすぐに完全に行う。記事・版・メディアのファイル・APIキー・Webhook・所属・招待・ジョブ・予算などの設定と、ワークスペースのDBのスキーマとロールを消す。元に戻す手段はない（戻すにはバックアップから復旧する）。
  - 利用者のアカウントは消さず、所属だけを外す。個人トークンからは、そのワークスペースを外す。
  - 監査ログの行は消さず、通常の保存期間まで残す（事故の後から調べられるように）。削除の操作はインスタンス全体の監査ログに記録し、管理者に通知する。
  - 削除の前にデータを書き出す機能は作らない。保存はバックアップの手順に任せる。
- 招待は、相手が既存の利用者でも、本人の承諾があって初めて所属させる。招待の操作への応答は、相手が既存の利用者かどうかで変えない。
- ワークスペースの管理者に見えるのは、自分のワークスペースの所属者だけ。他のワークスペースの利用者の存在を知る手段を作らない。
- 所属者の一覧は、ワークスペースの管理者とサーバー管理者が見られる。管理者は、他の所属者に「所属者の一覧の閲覧」の権限を個別に付与できる。この権限はM1から入れる（Q190）。
- ワークスペースの管理者がパスワードや多要素認証のリセットを発行できるのは、自分が管理者であるワークスペースにしか所属していない利用者だけ（詳細は `13-security.md`）。

## 組織（2026-11-25、持ち主の判断）

1つのインスタンスに複数の企業を入れられるように、ワークスペースの上に「組織」の層を置く。人のレビューが必須の領域なので、PRを小さく分けて進める。データの持ち方、移行、管理画面の細部は、実装の前に決める。

### 組織とワークスペース

- すべてのワークスペースは、どれか1つの組織に属する。ワークスペースを別の組織に移す操作は作らない。
- 導入したときに「既定の組織」を自動で作り、最初のサーバー管理者をその組織の管理者にする。今あるワークスペースは、移行のときに既定の組織に入れる。
- 組織が1つしかない間は、管理画面で組織を選ぶ欄を出さない。1社だけで使う人には、今までと同じ見え方にする。
- 既定の組織にも、ほかの組織と同じ決まり（上限、監査ログ）を当てはめる。ただし、組織の上限は既定では設けない（ワークスペースごとの上限は、これまでどおり既定値を持つ。`13-security.md`「運用」）。

### 組織を作る人と、組織の管理者

- 組織を作れるのは、サーバー管理者だけ。組織の削除も、サーバー管理者だけが行い、組織の名前の入力と直前の本人の確認（再認証）を求める。
- 組織の管理者は、次のことができる。
  - 組織の中にワークスペースを作る。作れる数の上限は、サーバー管理者が組織ごとに決める。
  - 組織のワークスペースを削除する。サーバー管理者の削除と同じく、ワークスペースの名前の入力と直前の本人の確認を求め、個人トークンでは行えない。
  - 組織のすべてのワークスペースの所属者と監査ログを見る。
  - 組織の所属者を招待し、組織のワークスペースのロールを付ける。招待は、これまでの招待と同じ規則に従う（本人の承諾、SMTPがないときの扱いなど）。
  - 組織の上限の範囲で、各ワークスペースに予算と上限を割り振る（`10-llm-and-budget.md`）。
  - 組織のOIDCの接続先と、組織の監査ログの書き出し先を設定する。
- 組織の管理者は、記事を直接は扱えない。記事を扱うには、自分にワークスペースのロールを付ける。その操作は監査ログに残し、そのワークスペースの管理者にも見えるようにする。
- 組織の管理者は、多要素認証を設定しないと管理操作ができない（ワークスペースの管理者と同じ。SSOでもCMS側のパスキーを必須とする）。
- 組織の管理者の付与と取り上げは、サーバー管理者と、その組織のほかの管理者が行える。

### 組織どうしの分離

- 組織の管理者どうしは互いに信頼しない（`13-security.md` の脅威モデル）。ある組織の管理者が、権限の操作・リセット・招待・資源の消費などを通じて、ほかの組織のデータや利用者に影響を与えられてはならない。
- 1人の利用者は、複数の組織に所属できる（制作会社やフリーランスを想定）。
- 組織の管理者に見えるのは、自分の組織の所属者だけ。ほかの組織の存在や所属者を知る手段を作らない。
- 組織の管理者がパスワードや多要素認証のリセットを発行できるのは、その組織にしか所属していない利用者だけ。ワークスペースの管理者の規則（自分が管理者であるワークスペースにしか所属していない利用者だけ）は、これまでどおり。
- 組織のOIDCでのJITのドメインは、サーバー管理者だけが組織に割り当てる。ほかの企業のドメインを横取りされないため。1つのドメインは1つの組織にだけ割り当てられる（`13-security.md`「OIDC/SSO」）。

### 組織の上限と予算

- サーバー管理者が、組織ごとに上限を決める: ワークスペースの数、メディアの容量の合計、LLMと埋め込みのトークン数の月ごとの合計。
- 組織の管理者は、その範囲で各ワークスペースに割り振る。組織の合計の上限に達したら、ワークスペースに残りがあっても止める（原則9、`10-llm-and-budget.md`「組織の上限」）。

### 組織の監査ログと通知

- 組織の単位の監査ログ（ワークスペースの作成と削除、所属とロールの変更、組織の管理者の付与、OIDCの設定、上限と予算の割り振り、組織の管理者が自分に付けたロール）を記録する。組織の管理者とサーバー管理者が見られる。
- 組織ごとに、監査ログの外部への書き出し先を設定できる。
- ログインの失敗の急増などの通知は、その組織の所属者に関するものだけを組織の管理者に出す。インスタンス全体の事象は、これまでどおりサーバー管理者だけに出す。

## 監査ログ（Q80, Q81）

記録はM1から始める。画面と外部への書き出しはM2（Q88）。

### 記録するもの

- 重い操作を記録する: ログイン、ロールや権限の変更、APIキーの発行と失効、LLMの接続設定と予算の変更、質問ログの閲覧、編集の引き継ぎ、スキーマのデプロイ、訂正としての公開、訂正による予約の自動取り消し（Q133）、版の本文の抹消（Q134）、MCPでの下書きの作成と変更、公開の終了の予約と取り消し、署名の鍵の入れ替え、組織の操作（2026-11-25）など。
- 記事の内容の変更は版の履歴に任せ、監査ログには「誰が、どの記事の、どの版を作ったか」のIDだけを残す。
- **記事の本文や訪問者の質問文などの内容は一切書かない。** IDと操作の種類だけを残す。
- 例外として、管理者への通知の急増の記録（ログイン失敗・回数制限への到達。インスタンス単位）には、件数・期間と、件数の多い順に最大10件ずつのIPアドレス・利用者のID・メールアドレスを残す。メールアドレスは存在するアカウントのものだけとし、存在しないアドレスへの試行は件数だけにする（入力された任意の文字列を残さない）。インスタンス単位の記録なので、サーバー管理者とインスタンス全体の書き出し先にだけ出る（Q174の補足、M2の計画の15番）。

### 保護と保存期間

- 監査ログは追記のみ。管理者であっても、管理画面や管理APIから編集・削除できない。
- DBの権限でも守る。普段の処理用のDBのロールからは、監査ログのテーブルのUPDATEとDELETEの権限を取り上げる。保存期間を過ぎたものの削除は、専用のロールだけが行う（Q111）。
- 保存期間は設定でき、既定は1年程度。期限を過ぎたものは自動で削除する。

### 閲覧の範囲

- インスタンスとワークスペースに分ける。
  - ワークスペースの管理者は、自分のワークスペースのログだけを見られる。
  - インスタンス全体のログ（エンドポイントの許可リストの変更、ワークスペースの作成、テンプレートのデプロイなど）は、サーバー管理者だけが見られる。
- サーバー管理者がワークスペースのデータを操作したとき（リセットの発行、所属の変更など）は、そのワークスペースの監査ログにも記録し、ワークスペースの管理者が見られるようにする（Q122）。

### 外部への書き出し

- 標準出力・ファイル・Webhookなどに、1行1件のJSON形式で同時に書き出せる。
- 外に書き出したものはCMSの自動削除の対象外とし、保管は運用者の責任とする。
