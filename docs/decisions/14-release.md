# v1.0 の公開（配布物・リリース・手順書・公開前の確認）

M4 までで全機能がそろったので、M5 で v1.0 の公開の準備をする（2026-11-05）。セキュリティの決まり（`13-security.md` の「依存ライブラリと配布物」「第三者の視点での確認」「侵入テスト」）は、そちらが正。ここには、その進め方を書く。

## M5 の進め方

1. `13-security.md` で「M1から」と決めたのに入っていないものを先に入れる: CIの依存の検査（Rustは `cargo-deny` で脆弱性・ライセンス・取得元。Node.jsは `npm audit --audit-level=high`）、依存の自動の更新提案（Dependabot）、`Cargo.toml` と `package.json` をCODEOWNERSの対象にすること、`LICENSE`（Apache-2.0）とリポジトリ直下の `README.md`。検査で見つかった依存の問題は、一覧にして持ち主が判断する。
2. `SECURITY.md`（下記）。
3. 配布の準備（下記の「配布物」「リリース」）。
4. 手順書（下記）。
5. 2回目の第三者の確認（下記）と、指摘への対応。
6. 侵入テスト（下記）と、指摘への対応。
7. 持ち主のブログで、v1.0 の候補の版を確かめてから、v1.0 のタグを付ける。

## 配布物

- コンテナイメージ（CMSのサーバー。GitHub Container Registry）。
- サーバーのバイナリ（Linux の x86_64 と arm64。GitHub Releases）。
- npm のパッケージ: CLI と Nuxt モジュール。それらが使う共有のパッケージ（editor-schema・converter・preview）も公開する。擬似LLMは配らない。
- 配るものには、OIDCによる鍵なしの署名（Sigstore の cosign）と SBOM を付ける（`13-security.md`）。

## リリース

- ふだんの確認はローカルで行う。GitHub Actions は、タグを付けたときだけ動くリリースのワークフローに使う（鍵なしの署名が GitHub の OIDC を前提とするため）。
- リリースのワークフローは、ビルド、公開、署名、SBOM の添付を行う。外部のアクションはコミットのSHAで固定し、権限は必要な分だけにする（`13-security.md`）。

## SECURITY.md

- 報告の窓口は、GitHub の非公開の脆弱性報告（Private vulnerability reporting）。
- セキュリティの修正は、最新のマイナー版にだけ出す。
- 英語と日本語で書く。

## 手順書

- `docs/manual/` に、読む人ごとに3冊を置く。v1.0 では日本語だけ。
  - `operator/`: サーバー管理者向け（導入、設定ファイル、更新、バックアップと復旧、事故対応、監視と監査ログの書き出し、ワークスペースの作成と天井）。
  - `developer/`: 開発者向け（テンプレートとCLI、組み込みJS、配信API、Nuxtモジュール、Webhookの受け方と署名の書式、回答APIの扱い）。
  - `editor/`: 編集者・ワークスペースの管理者向け（編集者の章と、ワークスペースの管理者の章）。
  - `reference/`: 3冊が共通で参照するもの（用語集、ロールと権限の一覧、エラーコードの一覧）。
- 同じことを2か所に書かない（原則2）。共通のものは `reference/` にだけ書き、各冊子からリンクする。
- 画面の画像は入れない。画面やボタンの名前は、管理画面の翻訳ファイルの文言をそのまま使う。
- `13-security.md` などで「手順書に書く」と決めたこと（バックアップ、事故対応と報告義務の案内、Webhookの署名の書式、ローカルのLLMを勧めること、マスクの限界など）は、該当する冊子の該当する手順のところに書く。
- サーバー管理者向けと開発者向けは、v1.0 でひととおり書く。編集者・ワークスペースの管理者向けは、v1.0 では主な作業に絞り、全画面の網羅は公開の後にする。

## 公開前の確認

- **2回目の第三者の確認**: M1 前の回（`docs/history/2026-10-09-security-review.md`）と同じやり方。設計の議論を見ていない別のAIに、決定の文書とコードだけを渡し、攻撃者の視点で確かめさせる。時期はほかの作業の後、公開の直前。結果は `docs/history/` に残し、対応は持ち主が決める。
- **侵入テスト**: 外部への依頼は持ち主が行う。依頼に渡す資料（範囲、動かし方）と、試験用の環境の Docker Compose を用意する。
- **持ち主のブログでの確認**: 公式の Docker Compose で動かしているブログを v1.0 の候補の版に上げ、手順書のとおりに更新とバックアップ・復旧ができるかを試す。
