# スキーマと配信API

## スキーマ定義

- スキーマはコードが正。開発モードでは管理画面のGUIで編集し、ファイルに書き出す。
- 構造（フィールド、ロケールの一覧、AIへの公開可否、URLテンプレート、確認期限など）は**JSONのデータファイル**に書く。JSON Schemaを用意し、エディタで補完と検証を効かせる（Q49, Q50）。
- 関数（URL生成関数、カスタムノードの変換関数、フック）は**TSファイル**に分け、データファイルからパスで参照する（Q49）。
- CLIがデータファイルと関数を1つのマニフェスト（JSON）にまとめ、管理画面とSDK用の型もそこから生成する（Q49）。
- 本文のノードの定義はTiptapの拡張機能が正。CLIが拡張機能から取り出してマニフェストに書き込む（Q57）。ノードの種類と属性に加え、content式を「許可する子ノードの一覧」に簡略化して書き出す（Q142）。
- 多言語は**ドキュメント単位**でローカライズする（Q154）。ロケールごとに、すべてのフィールドを持つ独立した記事を作り、同じ記事の翻訳どうしを**翻訳グループのID**で結ぶ。全ロケールで共有するフィールドは持たない。
  - 他の記事を指す参照フィールド（シリーズ、前提知識など）は、記事ではなく翻訳グループを指す。配信時に同じロケールの記事へ解決し、同じロケールの公開中の記事がなければ返さない（Q157）。
  - 当初の「フィールド単位でローカライズする」から変更した。共有フィールドがあると、版・訂正・予約・抹消・ロックのすべてに他のロケールへの波及が生じ（Q143、Q147〜Q150）、複雑さに見合う利点がブログでは小さいため。
- 拡張はフック＋カスタムフィールド。UIの拡張は将来。

### メモ書き（Q51）

- JSONはコメントを書けないため、フィールドやコンテンツタイプに次のプロパティを持たせる。どちらもGUIで編集でき、書き出しで消えない。
  - `description`: 編集者向けの説明。管理画面の入力欄にヘルプとして表示する。
  - `devNote`: 開発者向けのメモ。編集者には表示しない。
- `devNote` は、スキーマ情報を返すAPI、配信API、AI向け素材、LLMへのプロンプトのいずれにも含めない。

### 書き出しの書式（Q51）

- GUIからの書き出しでは、キーの順番と書式（インデントなど）を固定し、変更のない部分に差分を出さない。

## ワークスペースとテンプレート（Q52）

- ワークスペースは「どのテンプレートを使うか」だけを持つ。スキーマの実体はリポジトリ内のテンプレートのファイル。
- テンプレートを指定せずに作ったワークスペースは、テンプレートの名前を `default` として記録する。テンプレートのデプロイを実装するときに見直す（Q191）。
- 本番の管理画面ではテンプレートからワークスペースを作成できる。スキーマの変更はデプロイ経由。
- テンプレートを変更してデプロイすると、それを使うすべてのワークスペースに反映される。
- ワークスペース固有の構造が必要な場合は、新しいテンプレートを作る。

## 移行（Q53）

- 移行はワークスペースごとに別のトランザクションで行う。各ワークスペースは適用済みのスキーマのバージョンを持つ。
- 移行に失敗したワークスペースは「移行待ち」にして再試行する。移行待ちの間も配信は続け、そのワークスペースの編集だけを止める。
- 配信は、各ワークスペースに適用済みのバージョンのスキーマで行う。そのため、GraphQLスキーマは（テンプレート, バージョン）ごとに保持する。古いバージョンは、そのテンプレートを使うすべてのワークスペースの移行が終わった時点で捨てる（Q130）。
- CLIが変更を解析し、追加系（後方互換）と破壊系（フィールドの削除、型の変更など）に分類する。
  - 追加系は通常どおり適用する。
  - 破壊系は明示的な指定がない限りデプロイを拒否し、「追加 → データ移行 → 削除」の段階を踏ませる。

## 配信API

- GraphQL。キャッシュはPersisted Queries＋GET配信と、利用者のサイト側のキャッシュを前提とする。サイトはSSG・ISR・SSRのいずれでもよい（Q145、`01-architecture.md`）。
- スコープ付きのAPIキーが必須。キーのないリクエストは拒否する。
- ブラウザから直接呼ばせる公開キーは作らない（Q13）。
- 本番では登録済みのクエリだけを受け付ける。登録はサイトのビルド時またはデプロイ時にCLIが、読み取り用とは別の権限のキーで行う。APIキーごとの回数制限と応答の大きさの上限を設ける。回数制限の既定値は、キーの用途（ビルド用・サーバー配信用）で分ける。用途はスコープとは別の属性で、権限は変えない（Q94, Q145, Q153、詳細は `13-security.md`）。
- 配信APIのURLにはワークスペースIDを含め、APIキーのワークスペースと照合する。応答は既定で共有キャッシュに載せない（Q125、詳細は `13-security.md`）。
- GraphQLの実装には async-graphql の動的スキーマ機能を使う。デプロイ時にテンプレートのバージョンごとのGraphQLスキーマを組み立ててメモリに保持し、APIキー → ワークスペース → テンプレートと適用済みのバージョン → スキーマの順に引く（Q55, Q130）。URLのワークスペースIDとAPIキーのワークスペースが一致しない場合は拒否する（Q125）。採用時点でリリース状況と動的スキーマ機能の成熟度を確認する。

### 互換性の保護（Q54）

- デプロイ前に、CLIが登録済みのすべてのPersisted Queriesを新しいスキーマで検証し、1つでも壊れるならデプロイを拒否する（明示的な指定で強行は可能）。
- フィールドを削除する前に、GraphQLの `@deprecated` を付けて一定期間残す。非推奨のフィールドを使っている登録済みクエリを管理画面に一覧表示する。
- クエリごとに最終使用日時を記録し、一定期間使われていないクエリは検証の対象から外す。ビルドやデプロイのたびの再登録も「使用」として数える。検証の対象から外す前に、管理画面で知らせる（Q151）。

### エラー（Q79）

- 状態コードは、認証・認可の失敗（他のワークスペースを含む）は 401・403・404、検証の失敗・未登録のクエリ・移行待ちの編集は 4xx、回数制限は 429、下書きのリビジョン番号の食い違いは 409 とする（Q185）。
- APIのエラーには、機械的に判別できるコードを付ける。コードとメッセージは英語。管理画面はコードから各言語の文言を表示する。
