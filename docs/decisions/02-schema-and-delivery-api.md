# スキーマと配信API

## スキーマ定義

- スキーマはコードが正。開発モードでは管理画面のGUIで編集し、ファイルに書き出す。
- 構造（フィールド、ロケールの一覧、AIへの公開可否、URLテンプレート、確認期限など）は**JSONのデータファイル**に書く。JSON Schemaを用意し、エディタで補完と検証を効かせる（Q49, Q50）。
- 関数（URL生成関数、カスタムノードの変換関数、フック）は**TSファイル**に分け、データファイルからパスで参照する（Q49）。
- CLIがデータファイルと関数を1つのマニフェスト（JSON）にまとめ、管理画面とSDK用の型もそこから生成する（Q49）。
- 本文のノードの定義はTiptapの拡張機能が正。CLIが拡張機能から取り出してマニフェストに書き込む（Q57）。ノードの種類と属性に加え、content式を「許可する子ノードの一覧」に簡略化して書き出す（Q142）。
- 多言語は**ドキュメント単位**でローカライズする（Q154）。ロケールごとに、すべてのフィールドを持つ独立した記事を作り、同じ記事の翻訳どうしを**翻訳グループのID**で結ぶ。全ロケールで共有するフィールドは持たない。
  - 他の記事を指す参照フィールド（シリーズ、前提知識など）は、記事ではなく翻訳グループを指す。配信時に同じロケールの記事へ解決し、同じロケールの公開中の記事がなければ返さない（Q157）。
  - 当初の「フィールド単位でローカライズする」から変更した。共有フィールドがあると、版・訂正・予約・抹消・ロックのすべてに他のロケールへの波及が生じ（Q143、Q147〜Q150）、複雑さに見合う利点がブログでは小さいため。
- 拡張はフック＋カスタムフィールド。UIの拡張は将来。

### 画像のフィールド（2026-11-13）

- フィールドの型に `image`（画像）を加える。記事のサムネイルなどに使う。v1.0 の前に入れる（持ち主の判断。当初の M5 の範囲の外）。
- 値はメディアのID・代替テキスト・装飾画像の印で、本文の画像のノードと同じ属性を持つ。1つのフィールドに入るのは1枚だけ（複数は将来）。
- 保存のときに、メディアがそのワークスペースにあり、削除されていないことを確かめ、そうでなければ拒否する（INV-IMG-03）。本文の画像のメディアIDは、従来どおり形だけを確かめる。
- 公開のときは、本文の画像と同じく、代替テキストか装飾画像の印がなければ公開できない（INV-IMG-01）。
- 配信APIでは、URL・幅・高さ・代替テキスト・装飾画像の印を持つ型で返す。メディアが削除されていれば `null` を返す。削除済みかどうかは、配信のたびに確かめる（INV-IMG-02、原則3）。
- あわせて、サイズ違いの画像のURL（`srcset` 用。幅と形式ごと）も返す（2026-11-25、`13-security.md`「画像の変換」）。
- メディアの使用状況（削除の確認と、抹消の削除の候補）には、画像のフィールドで使っているものも含める（INV-PUB-06）。
- 検索・質問応答の対象（`searchable`）と、AI向けのMarkdown版（`aiMarkdown`）には含めない。
- SNSへの共有ボタンと OGP（`og:image` など）はサイト側で作る。CMSは題名・要約・URL・画像のフィールドを返すだけで、SNSへの自動の投稿は持たない。必要なら、記事の公開の Webhook を受けたサイト側の仕組みで行う（原則1）。

### フィールドの型（2026-11-25、持ち主の判断）

- これまでの型（`text`・`slug`・`richtext`・`reference`・`image`）に、次の型を加える。ブログ以外の用途（ドキュメント、報道、企業のサイト）でも使えるようにするため。
  - 数値
  - 真偽値
  - 日付・日時
  - 選択肢（テンプレートで決めた値の中から1つを選ぶ）
  - グループ（いくつかのフィールドをまとめて、繰り返し持てる。例: FAQ の「質問と答え」）
- ファイル（PDFなどの添付）と、形を決めないJSONの型は入れない。ファイルはメディアの検査（形式の判定と無害化）を新しく作る必要があり、JSONは入力を検証できないため。
- 値の検証は、ほかの型と同じく保存のときにRustで行い、型に合わない値（選択肢にない値を含む）は保存しない。必須の検査は公開のときと移行のときに行う。グループの中のフィールドも同じ規則に従う。
- 型の変更は、これまでどおり破壊的な変更として扱う（下記「移行」）。
- 細部（数値の範囲、タイムゾーン、選択肢の表示名、グループの入れ子の深さと件数の上限、検索とAI向けのMarkdown版での扱い）は、実装の前に決める（`01-architecture.md`「未決事項」）。

### 本文のHTML（2026-11-25、持ち主の判断）

- 配信APIで、`richtext` のフィールドの構造だけのHTMLを、Tiptap の JSON とあわせて返す。JSON はこれまでどおり返す。描くだけのサイトは HTML を使い、作り込みたいサイトは JSON を使える。
- HTML は、本文の変換器（`03-content-and-editing.md`「本文」）で作る。見た目（CSS、`style` 属性）は付けず、要素とクラス名だけにする（原則1）。すべての文字列をエスケープし、リンクのスキームと埋め込みの提供元の規則を守る（`13-security.md`「本文」）。
- HTML は公開のときに作って保存し、配信のたびには変換しない。変換器の版が変わったら、Markdown版と同じく作り直す。
- 本文を抹消した版の HTML も消す。
- GraphQL での返し方（既存の登録済みのクエリを壊さない形）と、カスタムノードの HTML への変換関数の扱いは、実装の前に決める。

### 執筆支援の項目の指定（2026-11-17）

- タイトルの案は、既存のコンテンツタイプの指定 `titleField`（記事のタイトルのフィールド）に当てる。要約の案は、新しい任意の指定 `summaryField`（記事の要約のフィールド）に当てる（`10-llm-and-budget.md`）。
  - 当初は `assist: { title, summary }` としたが、`titleField` と同じ情報を2か所に書くことになるため、`titleField` と同じ形の `summaryField` に改めた（2026-11-17、持ち主の判断。原則2）。
- どちらも、そのコンテンツタイプの `text` 型のフィールドとして実在し、互いに別のフィールドであること。CLIのチェックとサーバーのデプロイの検査の両方で確かめ、満たさなければデプロイを止める（原則10）。
- 指定がない項目の案は出さない。配信APIには影響しない。

### メモ書き（Q51）

- JSONはコメントを書けないため、フィールドやコンテンツタイプに次のプロパティを持たせる。どちらもGUIで編集でき、書き出しで消えない。
  - `description`: 編集者向けの説明。管理画面の入力欄にヘルプとして表示する。
  - `devNote`: 開発者向けのメモ。編集者には表示しない。
- `devNote` は、スキーマ情報を返すAPI、配信API、AI向け素材、LLMへのプロンプトのいずれにも含めない。

### 表示名（2026-11-21）

- フィールドとコンテンツタイプに、任意の `label` を持たせる。管理画面の入力欄・一覧・新しい記事の画面などで、`name`（内部名）の代わりに出す。
  - 書き方は管理画面の言語ごと: `"label": { "ja": "タイトル", "en": "Title" }`。
  - 書けるキーは管理画面が対応する言語（`ja`・`en`）だけ。ほかのキー、空の値、改行を含む値、長すぎる値（50文字まで）は、CLIのチェックとサーバーのデプロイの検査の両方で止める（原則10）。
  - 管理画面の言語の `label` がなければ `name` を出す。別の言語の `label` では代えない（画面に別の言語を混ぜない）。
  - 表示だけの情報なので、変えても破壊的変更にはならない。配信API・AI向け素材・LLMへのプロンプトには含めない。
- コンテンツのロケール（`ja` など）は、スキーマを変えずに、管理画面が言語名にして「日本語（ja）」の形で出す。
- 管理画面の利用者が内部名（`title`・`post`・`ja`）を見ずに済むようにするため（2026-11-20 の管理画面の点検、持ち主の判断）。

### 書き出しの書式（Q51）

- GUIからの書き出しでは、キーの順番と書式（インデントなど）を固定し、変更のない部分に差分を出さない。

## ワークスペースとテンプレート（Q52）

- ワークスペースは「どのテンプレートを使うか」だけを持つ。スキーマの実体はリポジトリ内のテンプレートのファイル。
- テンプレートを指定せずに作ったワークスペースは、テンプレートの名前を `default` として記録する。テンプレートのデプロイを実装するときに見直す（Q191）。
- 本番の管理画面ではテンプレートからワークスペースを作成できる。スキーマの変更はデプロイ経由。
- テンプレートを変更してデプロイすると、それを使うすべてのワークスペースに反映される。
- ワークスペース固有の構造が必要な場合は、新しいテンプレートを作る。
- 1つのワークスペースが使うテンプレートは1つだけとする。ブログとドキュメントを1つのサイトで持つ場合などは、ワークスペースを分ける。手順書で案内する（2026-11-25）。

### 同梱のテンプレート（2026-11-25、持ち主の判断。2026-11-22 の「2つ目のテンプレートは作らない」を改めた）

4種類の対象の利用者（`01-architecture.md`「製品としての位置づけ」）に向けて、次の見本のテンプレートを同梱する。企業のオウンドメディアは blog で兼ねる。

- **blog**: 今の記事（`post`）に、カテゴリー、タグ、著者のコンテンツタイプと、それらへの参照を加える。
- **docs**（新規）: ページ（親ページへの参照、並び順の数値、製品のバージョンの選択肢）と、製品のバージョンの一覧。製品のバージョンごとに記事を分けて書く。
- **news**（新規）: 記事（記者は著者への参照、速報の印、カテゴリー）、著者、カテゴリー。解禁日時（エンバーゴ）は予約公開で代える。

どれも同梱のテンプレートとして、管理画面からデプロイできる（`13-security.md`「デプロイ」）。各フィールドの細部は、実装の前に決める。

### SDL の書き出し（2026-11-25）

- CLI で、テンプレートから配信APIの GraphQL のスキーマ（SDL）を書き出せるようにする。サーバーの動的スキーマと同じマニフェストから作り、同じ内容になることをテストで確かめる（原則2）。
- 本番の配信APIのイントロスペクションは無効のまま（INV-GQL-04）。SDL はサーバーに問い合わせずに作る。

## テンプレートの切り替え（2026-11-11、持ち主の判断。M5 の例外）

ワークスペースが使うテンプレートを、作った後から、デプロイ済みの別のテンプレートに切り替えられる。記事があっても切り替えられる。

- **対応づけ:** 古いテンプレートのコンテンツタイプとフィールドを、新しいテンプレートのどれに引き継ぐかを、画面で対応づける。既定では名前の同じものを対応づける。型の合わないフィールドは対応づけられない。対応づけのないものは消える。
- **データが消えるとき:** 試行で、消えるコンテンツタイプとフィールド、壊れる登録済みのクエリ、必須なのに値のない記事を見せる。消えるものがあれば、明示的な指定と直前の本人の確認（再認証）がなければ行わない（INV-SCH-08）。消えるデータは、切り替えの前に JSON で書き出してダウンロードできる。
- **過去の版:** 過去の版の本文も、対応づけに従って新しいテンプレートの形に置き換える。版の ID・番号・公開日時・訂正の記録は残す（INV-PUB-03 を改めた）。置き換えた後は、切り替える前の本文を取り戻せない（書き出した JSON とバックアップに残る）。
- **行える人:** サーバー管理者と、重い権限「テンプレートの切り替え」を付与されたワークスペースの管理者（INV-SCH-09）。監査ログに残し、ワークスペースの管理者とサーバー管理者に通知する。
- **選び方:** ワークスペースを作るときと切り替えるときは、テンプレートをプルダウンで選ぶ。作るときは、デプロイ済みのものに加えて「その他（名前を入力）」も選べる（CLI でこれからデプロイする名前）。ただし、デプロイ済みのテンプレートが1つだけのときは、作るときはその1つに固定し、プルダウンも「その他」も出さない（2026-11-22、持ち主の判断。別の名前を使うときは、先にそのテンプレートをデプロイする）。切り替えるときは、デプロイ済みのものだけ。

## 移行（Q53）

- **テンプレートの版を持たない**（2026-11-23、持ち主の判断。Q130 を改めた）: サーバーは、テンプレートごとに最新のマニフェストを1つだけ持つ。デプロイに版の番号を付けず、利用者には最後にデプロイした日時を見せる。ワークスペースは版を持たず、「まだ適用していない」か「適用済み」かだけを持つ。1つのテンプレートを使うワークスペースが1つという運用では、ワークスペースごとに版がずれることが起きず、版ごとに管理する仕組みが見合わないため。記事の版（公開の履歴）は別のもので、変えない。
- **全部適用するか、全部やめるか**（2026-11-23）: デプロイでは、そのテンプレートを使うすべてのワークスペースの移行を、1つのトランザクションで行う。1つでも失敗すれば、デプロイ全体を取りやめ、どのワークスペースもデプロイの前のままにする。移行待ちの状態は持たない（以前は、失敗したワークスペースだけを移行待ちにして、古い版のスキーマで配信を続けていた）。
- **データの持ち方**（Q201）: コンテンツタイプごとのテーブル（`ct_<名前>`）に、フィールドを1列ずつ（`f_<名前>`）持たせて下書きを置き、移行はこのテーブルへのDDLで行う。公開した版は、公開した時点のフィールドのJSONのスナップショットとして書き換えずに残し（本文の抹消を除く）、配信はそこから読む。必須のフィールドは、公開のときと移行のときにコードで確かめる。移行のときは、公開中の版に加えて、予約公開を待っている版（予約版）も確かめ、新しいスキーマに合わない予約版（必須のフィールドが空、外すノードやマークを使っている）があればデプロイ全体を止める。予約版は予約したときの内容のまま公開されるため（2026-11-24、持ち主の判断。デプロイで予約を取り消す案、公開のときに確かめ直す案より、原則10に合うものを選んだ）。公開した版には、公開したときのテンプレートの版を記録しない（2026-11-23、`schema_version` の列を削除する）。
- **この仕組みに上げるとき**（2026-11-23）: 移行待ちのワークスペースが残っていれば、DB の移行を止め、先に古いサーバーで解消するよう求める。
- CLIが変更を解析し、追加系（後方互換）と破壊系（フィールドの削除、型の変更など）に分類する。
  - 追加系は通常どおり適用する。
  - 破壊系は明示的な指定がない限りデプロイを拒否し、「追加 → データ移行 → 削除」の段階を踏ませる。

## 配信API

- GraphQL。キャッシュはPersisted Queries＋GET配信と、利用者のサイト側のキャッシュを前提とする。サイトはSSG・ISR・SSRのいずれでもよい（Q145、`01-architecture.md`）。
- スコープ付きのAPIキーが必須。キーのないリクエストは拒否する。
- ブラウザから直接呼ばせる公開キーは作らない（Q13）。
- 本番では登録済みのクエリだけを受け付ける。登録はサイトのビルド時またはデプロイ時にCLIが、読み取り用とは別の権限のキーで行う。APIキーごとの回数制限と応答の大きさの上限を設ける。回数制限の既定値は、キーの用途（ビルド用・サーバー配信用）で分ける。用途はスコープとは別の属性で、権限は変えない（Q94, Q145, Q153、詳細は `13-security.md`）。
- 配信APIのURLにはワークスペースIDを含め、APIキーのワークスペースと照合する。応答は既定で共有キャッシュに載せない（Q125、詳細は `13-security.md`）。
- 公開版には、改ざんの検知のための署名を付けて返す（2026-11-25、`06-corrections-and-freshness.md`「改ざんの検知」）。
- サイトマップを作るための、公開中の記事のURLの一覧を返す（2026-11-25、`05-urls-and-redirects.md`「サイトマップ」）。
- GraphQLの実装には async-graphql の動的スキーマ機能を使う。デプロイ時にテンプレートごとのGraphQLスキーマを組み立ててメモリに保持し、APIキー → ワークスペース → テンプレート → スキーマの順に引く（Q55。2026-11-23 に、版ごとに持つのをやめた）。URLのワークスペースIDとAPIキーのワークスペースが一致しない場合は拒否する（Q125）。採用時点でリリース状況と動的スキーマ機能の成熟度を確認する。

### 互換性の保護（Q54）

- デプロイのとき、登録済みのPersisted Queriesを新しいスキーマで検証し、壊れるクエリが1つでもあれば、デプロイ全体を拒否する（どのワークスペースにも適用しない）。サーバー管理者が明示的に指定したときだけ、すべてのワークスペースに適用する（そのクエリは失敗するようになる）。2026-11-23、持ち主の判断で INV-SCH-03 を改めた。そのため、クエリを登録できる人は、同じテンプレートを使うほかのワークスペースへのデプロイを止められる（第三者の確認の R42）。1つのテンプレートを使うワークスペースが1つという運用では影響が小さく、サーバー管理者が明示すれば通せるので、これを受け入れる。手順書に書く。（2026-11-10 には、壊れるクエリを持つワークスペースだけを移行待ちに残す形で直していた。）
- フィールドを削除する前に、GraphQLの `@deprecated` を付けて一定期間残す。非推奨のフィールドを使っている登録済みクエリを管理画面に一覧表示する。
- クエリごとに最終使用日時を記録し、一定期間使われていないクエリは検証の対象から外す。ビルドやデプロイのたびの再登録も「使用」として数える。検証の対象から外す前に、管理画面で知らせる（Q151）。

### エラー（Q79）

- 状態コードは、認証・認可の失敗（他のワークスペースを含む）は 401・403・404、検証の失敗・未登録のクエリは 4xx、回数制限は 429、下書きのリビジョン番号の食い違いは 409 とする（Q185）。
- APIのエラーには、機械的に判別できるコードを付ける。コードとメッセージは英語。管理画面はコードから各言語の文言を表示する。
