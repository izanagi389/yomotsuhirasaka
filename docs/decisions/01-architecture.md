# 全体構成

## 目的と方針

- 製品名は yomotsuhirasaka（リポジトリ・イメージ・パッケージのスコープ）。コードの中の名前は短い `yomi` を使う（`yomi-server`、`yomi` コマンド、`NUXT_YOMI_*`、`<YomiBody>`、`yomi_key_`、DB の `yomi` スキーマなど。2026-11-08）。
- ブログ向けのヘッドレスCMS。持ち主が自分のブログで使いつつ、商用利用にも耐える品質を目指す。
- ヘッドレス型、ユーザー定義スキーマ、セルフホスト可能なOSS、開発者体験（DX）と編集者の使いやすさを重視する。
- ライセンスはApache-2.0。v1.0まではIssue報告のみ受け付け、公開後はDCOでコントリビューションを受け付ける。
- 実装はAIが担当し、持ち主は指示とレビューを担当する。

### 製品としての位置づけ（2026-11-25、持ち主の判断）

- 既存のCMSとは異なる機能を持ち、商品として通用する性質にする。ただし OSS（Apache-2.0）のまま広め、公式のクラウドは運営しない。
- 打ち出し方は「AI時代でも信頼される記事」。信頼（訂正、鮮度、出典、改ざんの検知、リンクと引用元の見張り）を中心に置き、AI向けの機能（AI向け配信、MCP、出典付きの回答）はそれを支える手段とする。
- 対象の利用者は、技術ブログを書く個人や小さなチーム、企業のオウンドメディア、製品のドキュメントやナレッジベース、報道や専門のメディアのすべて。
- 有償のサポートや寄付の案内は、持ち主が求めたときだけ書く。README・手順書・`SUPPORT.md` などに、求められずに書かない。

## 構成

| 部分 | 技術 | 備考 |
|---|---|---|
| サーバー | Rust | 性能（長時間接続の中継など）とメモリ使用量を重視（Q8, Q9） |
| 管理画面 | Nuxt | SPAとしてビルドし、Rustのサーバーから配信する。本番で動くのはRustのサーバーとPostgreSQLだけ（Q87） |
| CLI | Node.js | Tiptapの拡張機能からノード定義を取り出すため（Q57） |
| 公式連携部品 | Nuxtモジュール | AI向け素材、リダイレクト、訂正フィード、サイトマップ、プレビューなどの生成と受け側。ほかのフレームワーク向けの連携部品は作らず、APIだけで連携する方法を手順書で示す（下記「APIだけで連携する」） |
| DB | PostgreSQL 16以上（Q179） | pgvector、pg_bigm または PGroonga を同梱した公式Dockerイメージを提供（Q23） |
| LLM | 外部のOpenAI互換API | 埋め込みも生成も同じ口。CMSのプロセス内でモデルを動かさない（Q6, Q7） |

リポジトリはモノレポとする。サーバーがRustになったため、型の共有はスキーマから生成したマニフェストと型を通して行う（Q49）。

### 実行構成（Q129。2026-11-25 に変更）

- 障害に強くするため、v1.0 から、1つのインスタンスを複数のプロセス（台数）で動かせるようにする（2026-11-25、持ち主の判断。当初は「v1.0は1インスタンス＝1プロセス」）。
- どのプロセスも同じ役割を持ち、ロードバランサーで振り分ける。特定のプロセスに固定する必要はない（回答のストリーミング（SSE）も、受け付けたプロセスで完結させる）。
- 回数の制限、同時編集のソフトロック、スキーマの世代、ログインの失敗の数えなど、プロセスをまたいで一致しなければならない状態の正本はDBに置く。メモリは写しとして使い、写しが古くても約束を破らない作りにする。
- ジョブ（埋め込み、Webhookの送信、夜間の再計算など）のキューはPostgreSQLに置く（`SKIP LOCKED`）。止まったプロセスが持っていたジョブは、ほかのプロセスが後で拾う。夜間の処理など、同時に1つだけ動かすものは、DBのロックで1つのプロセスだけが実行する。
- メディアの保存先は、どのプロセスからも同じファイルを読めるものにする（下記「メディア」）。
- 公式の Docker Compose に、2台構成の例を加える。約束のテストでも、2つのプロセスを立ち上げて確かめる。
- **メトリクス**: Prometheus の形式のメトリクス（リクエストの数と時間、ジョブの滞留、予算の消費など）を、管理用の別のポートから出す。公開するポートからは出さず、公式の Docker Compose では外にポートを開けない。記事の本文、質問文、秘密の値は含めない（原則7）。

### APIだけで連携する（2026-11-25）

Nuxt 以外のフレームワーク（Next.js、Astro など）では、連携部品を使わずに、APIだけで連携する。そのために次を用意する。

- 配信APIで、本文の構造だけのHTML（エスケープ済み、見た目は付けない）を返す（`02-schema-and-delivery-api.md`「本文のHTML」）。
- テンプレートから、配信APIの GraphQL のスキーマ（SDL）を CLI で書き出せるようにする。利用者は好きな道具で型を作れる。本番のイントロスペクションは無効のまま（INV-GQL-04）。
- 手順書の開発者向けに、記事の取得、本文の描画、プレビュー、回答APIの中継（SSE の形式）、Webhook の受け方を HTTP のやりとりとして書き、Next.js と Astro の短い例を載せる。

### 利用者のサイトの描画方式（Q145）

- 利用者のサイトは、SSG・ISR・SSR（およびそれらの組み合わせ）のいずれでもよい。どの方式でも配信APIはサーバー間で呼ばれ、APIキーはブラウザに出ない。
- キャッシュはサイト側で持つことを前提とする。SSRのサイトは閲覧のたびにCMSへ問い合わせうるため、手順書でNuxt側のキャッシュ（`routeRules` の `swr` など）を必ず使うよう案内する。
- Nuxtモジュールが生成するもの（`/llms.txt`、記事のMarkdown版、訂正一覧ページとフィード、リダイレクト設定など）は、ビルド時の生成と、サーバーのルートとして返す方式の両方に対応する。サーバーのルートはキャッシュ付きで返し、CMSからのWebhook（公開・訂正・抹消など）でキャッシュを消す。

## マルチテナント

- 1つのインスタンスの中に複数のワークスペースを持つ。公式クラウドは運営しない。
- データはPostgreSQLに保存し、コンテンツタイプごとにテーブルを持ち、ワークスペースごとにDBスキーマを分ける。
- ワークスペースは「どのテンプレートを使うか」だけを持ち、スキーマの実体はリポジトリ内のテンプレートのファイル（Q52）。詳細は `02-schema-and-delivery-api.md`。
- **組織**（2026-11-25、持ち主の判断）: ワークスペースの上に「組織」の層を置き、1つのインスタンスに複数の企業（組織）を入れられるようにする。すべてのワークスペースは、どれか1つの組織に属する。組織の管理者、上限と予算、組織ごとのSSO、組織の監査ログは `11-permissions-and-audit.md`「組織」。

## 認証（Q87）

- 認証はRustのサーバーで行う。ログイン、セッション、パスワードの保管、外部のOIDC/SSOとの接続をすべてRust側で扱う。
- 管理画面とCLIは、同じ管理APIの認証に乗る。
- パスワードの保管、セッション、OIDCは、実績のあるRustのライブラリを組み合わせる。暗号処理は自作しない。採用するライブラリは使う時点で保守状況を確認する。
- 外部のOIDC/SSOはオプションで接続できる。SSOの初回ログインは招待制が既定。ドメインのルールによる自動作成（JIT）は任意。OIDCの検証やアカウントのひも付けの規則は `13-security.md`（Q103）。OIDCの接続先は、インスタンスに加えて組織ごとにも設定できる（2026-11-25、`11-permissions-and-audit.md`「組織」）。
- ワークスペースの管理者どうし、組織の管理者どうしは互いに信頼しない前提で、権限と認証を設計する（Q101、`13-security.md` の脅威モデル）。

## メディア

- メディアの保存先は、ローカルのファイルシステムか、S3互換のオブジェクトストレージ（MinIO、Cloudflare R2、AWS S3 など）から選ぶ（2026-11-25。当初は「ローカルのファイルシステムのみ」）。複数のプロセスで動かすときは、S3互換のストレージか、すべてのプロセスから見える共有のディスクを使う。
- S3互換のストレージへの通信も、外部への送信の共通の仕組みを通す（`13-security.md`「外部への送信」）。同じネットワークの MinIO などは、サーバー管理者が内部宛先の例外として許可する。接続の秘密は、ほかの秘密と同じく暗号化して保存するか、環境変数かファイルで渡す。
- メディアは管理画面とは別のドメインから配信することを推奨の設定とする（Q96、詳細は `13-security.md`）。
- 画像は、配信のときに決まった幅と形式に変換して返せる（`13-security.md`「メディア」の「画像の変換」）。

## Webhook

- 署名付きのWebhookを送る。
- Webhookの本文には、記事の本文や下書きの内容を含めず、ワークスペースID・記事ID・翻訳グループID・ロケール・イベントの種類・公開URLだけを含める。受け手は必要なら配信APIで取り直す（原則7、Q160）。
- 記事の状態変化をイベントとして送る: 公開、更新、非公開化、削除、訂正として公開（Q48）、版の本文の抹消、公開設定の変更（外部AI向けの素材に含める、学習への利用の拒否など）、URLの変更（Q146）。
- サイト側のキャッシュ（SSRのサーバールートなど、Q145）とCDNの共有キャッシュ（Q141）は、これらのイベントで消す。イベントは共有キャッシュの有無にかかわらず送る（Q146）。
- このほか、「関連記事の一覧が変わった記事」（Q61）を送る。

## 未決事項

Q1〜Q202 は決着済み。2026-11-25 に加えた機能（M5）の細部は、それぞれの着手の前に持ち主に選択肢と推奨を示して決める。主なもの:

- フィールドの型: 数値の範囲と小数の扱い、日付と日時のタイムゾーン、選択肢の書き方（表示名を含む）、グループの入れ子の深さと件数の上限、新しい型を検索の対象・AI向けのMarkdown版に含めるか。
- テンプレート: blog・docs・news の各フィールドの細部と、docs の親ページの循環の防ぎ方。
- 本文のHTML: GraphQL での返し方（既存のクエリを壊さない形）、カスタムノードのHTMLへの変換関数を必須にするか。
- 画像の変換: 幅の一覧の既定値、同時の変換数の既定値、保存した変換後の画像の消し方。
- 組織: データの持ち方と移行、組織の管理者のロールの付け方、LLMの接続設定の3段（インスタンス・組織・ワークスペース）の上書きの細部。
- MCP: 提供する道具（tools）の一覧、個人トークンの範囲の名前。
- 署名: 署名する内容の正規化の方式。
- リンクと引用元の見張り: 1つのホストへの間隔、応答の大きさの上限。
- 似た質問のまとめ: まとめ方（しきい値など）。
