# 全体構成

## 目的と方針

- ブログ向けのヘッドレスCMS。持ち主が自分のブログで使いつつ、商用利用にも耐える品質を目指す。
- ヘッドレス型、ユーザー定義スキーマ、セルフホスト可能なOSS、開発者体験（DX）と編集者の使いやすさを重視する。
- ライセンスはApache-2.0。v1.0まではIssue報告のみ受け付け、公開後はDCOでコントリビューションを受け付ける。
- 実装はAIが担当し、持ち主は指示とレビューを担当する。

## 構成

| 部分 | 技術 | 備考 |
|---|---|---|
| サーバー | Rust | 性能（長時間接続の中継など）とメモリ使用量を重視（Q8, Q9） |
| 管理画面 | Nuxt | SPAとしてビルドし、Rustのサーバーから配信する。本番で動くのはRustのサーバーとPostgreSQLだけ（Q87） |
| CLI | Node.js | Tiptapの拡張機能からノード定義を取り出すため（Q57） |
| 公式連携部品 | Nuxtモジュール | AI向け素材、リダイレクト、訂正フィード、プレビューなどの生成と受け側 |
| DB | PostgreSQL 16以上（Q179） | pgvector、pg_bigm または PGroonga を同梱した公式Dockerイメージを提供（Q23） |
| LLM | 外部のOpenAI互換API | 埋め込みも生成も同じ口。CMSのプロセス内でモデルを動かさない（Q6, Q7） |

リポジトリはモノレポとする。サーバーがRustになったため、型の共有はスキーマから生成したマニフェストと型を通して行う（Q49）。

### 実行構成（Q129）

- v1.0は、1インスタンス＝1プロセスで動かす前提とする。
- ジョブ（埋め込み、Webhookの送信、夜間の再計算など）のキューはPostgreSQLに置く（`SKIP LOCKED`）。
- スキーマの世代や回数制限などの正本はDBに置き、メモリは写しとして使う。後から台数を増やせる道を残す。

### 利用者のサイトの描画方式（Q145）

- 利用者のサイトは、SSG・ISR・SSR（およびそれらの組み合わせ）のいずれでもよい。どの方式でも配信APIはサーバー間で呼ばれ、APIキーはブラウザに出ない。
- キャッシュはサイト側で持つことを前提とする。SSRのサイトは閲覧のたびにCMSへ問い合わせうるため、手順書でNuxt側のキャッシュ（`routeRules` の `swr` など）を必ず使うよう案内する。
- Nuxtモジュールが生成するもの（`/llms.txt`、記事のMarkdown版、訂正一覧ページとフィード、リダイレクト設定など）は、ビルド時の生成と、サーバーのルートとして返す方式の両方に対応する。サーバーのルートはキャッシュ付きで返し、CMSからのWebhook（公開・訂正・抹消など）でキャッシュを消す。

## マルチテナント

- 1つのインスタンスの中に複数のワークスペースを持つ。公式クラウドは運営しない。
- データはPostgreSQLに保存し、コンテンツタイプごとにテーブルを持ち、ワークスペースごとにDBスキーマを分ける。
- ワークスペースは「どのテンプレートを使うか」だけを持ち、スキーマの実体はリポジトリ内のテンプレートのファイル（Q52）。詳細は `02-schema-and-delivery-api.md`。

## 認証（Q87）

- 認証はRustのサーバーで行う。ログイン、セッション、パスワードの保管、外部のOIDC/SSOとの接続をすべてRust側で扱う。
- 管理画面とCLIは、同じ管理APIの認証に乗る。
- パスワードの保管、セッション、OIDCは、実績のあるRustのライブラリを組み合わせる。暗号処理は自作しない。採用するライブラリは使う時点で保守状況を確認する。
- 外部のOIDC/SSOはオプションで接続できる。SSOの初回ログインは招待制が既定。ドメインのルールによる自動作成（JIT）は任意。OIDCの検証やアカウントのひも付けの規則は `13-security.md`（Q103）。
- ワークスペースの管理者どうしは互いに信頼しない前提で、権限と認証を設計する（Q101、`13-security.md` の脅威モデル）。

## メディア

- メディアの保存先はローカルのファイルシステムのみ。
- メディアは管理画面とは別のドメインから配信することを推奨の設定とする（Q96、詳細は `13-security.md`）。

## Webhook

- 署名付きのWebhookを送る。
- Webhookの本文には、記事の本文や下書きの内容を含めず、ワークスペースID・記事ID・翻訳グループID・ロケール・イベントの種類・公開URLだけを含める。受け手は必要なら配信APIで取り直す（原則7、Q160）。
- 記事の状態変化をイベントとして送る: 公開、更新、非公開化、削除、訂正として公開（Q48）、版の本文の抹消、公開設定の変更（外部AI向けの素材に含める、学習への利用の拒否など）、URLの変更（Q146）。
- サイト側のキャッシュ（SSRのサーバールートなど、Q145）とCDNの共有キャッシュ（Q141）は、これらのイベントで消す。イベントは共有キャッシュの有無にかかわらず送る（Q146）。
- このほか、「関連記事の一覧が変わった記事」（Q61）を送る。

## マイルストーン

v1.0で全機能を揃えて公開する。それまでは非公開の内部マイルストーンで進め、M1から持ち主のブログで運用する（Q65, Q66, Q88）。

| M | 範囲 |
|---|---|
| M1 | CMSの基本機能（スキーマのJSONとCLI、PostgreSQL、本文の検証、GraphQL配信（APIキー、Persisted Queries）、下書き・公開・版、下書きの自動保存、管理画面とNuxtモジュールの最小限）。認証（Rust）と固定のロール。管理画面の多言語化の仕組み（日本語・英語）。公開の確認画面（変更されたセクションの一覧、代替テキストの確認）。Markdownの取り込みCLI（既存のブログからの移行。リダイレクト設定ファイルの書き出しを含む（Q132））。下書きの保存の楽観ロック（Q137）。多言語の翻訳グループ、複製による翻訳の作成、元の記事とその版の記録（Q154, Q159）。後から取り返せない記録（固定アンカーID、URLの保存と変更履歴、「訂正として公開」の記録、監査ログの記録）。URLはテンプレートのみ対応し、組み込みJSは入れない（Q82）。記事の公開設定のスイッチは保存と変更のWebhookだけを入れ、効果はM2（Q184）。AI系の機能は入れない。セキュリティの基盤（`13-security.md` のうち、プレビュー・チャットボット・配布物の署名以外）もM1から入れる。外部のOIDC/SSOもM1に入れ、M1の最後に実装する（Q126） |
| M2 | 組み込みJS・変換器・フック・カスタムノード（変換関数の必須化）、AI向け配信（Markdown版、`llms.txt`、学習拒否）、URL生成関数とリダイレクト、訂正フィード・削除済みアンカー・鮮度の公開、読了時間などの出し分け用メタデータ。翻訳グループの原文の更新の知らせと差分の表示（Q155, Q159）。重い権限の個別付与、レビュー依頼、予約公開、同時編集のソフトロック、「やること」画面と編集画面内の知らせ、プレビュー（ライブ・実サイト）、監査ログの画面と外部への書き出し、管理者への通知（Q174）。外部APIは使わない |
| M3 | 検索の基盤（共通のアクセス制御層、チャンク分割、埋め込み、キーワード検索）、関連記事、サイト内検索、埋め込みの費用見積もりと予算、擬似LLM |
| M4 | チャットボット（回答生成、判定先行のストリーミングとSDKの中継ヘルパー、予算切れの扱い、回答キャッシュ、質問ログ、語り口、LLM接続設定の上書き）。訪問者向けの回答と編集者向けの支援の予算。編集者向けのAI支援 |

現在のマイルストーンは、リポジトリ直下の `current-milestone` に書く。変更には持ち主の承認が必要（Q86）。
