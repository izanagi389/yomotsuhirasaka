# 侵入テストの環境での耐久性の確かめ（2026-11-11）

`docs/pentest/README.md` の「動かさないと分からない、次のものも見てください」を、侵入テストの環境（`deploy/pentest/`、本番の設定）で確かめた記録です。

AI のエージェントによる侵入テストは、AI の提供元の安全の仕組みに止められて行えませんでした（2026-11-10）。持ち主の判断で、攻撃としてではなく、自分のシステムの耐久性の確認として、Claude が短い負荷だけで確かめました。外部の侵入テストの代わりではありません。

- 確かめた版: `main` の `3432541`（#217〜#223 を含む）
- 環境: 1台の Mac（Apple Silicon）の Docker。Caddy を通して `https://cms.pentest.test` に送った。CMS は1プロセス
- 送り元: Compose のネットワークの中のコンテナ（`deploy/pentest` の seed のイメージ）。ホストの設定は変えていない

## 結果

| 項目 | 結果 | 判断 |
|---|---|---|
| 検索や配信のクエリを多数同時に送ったとき | 下の 1 | 問題なし |
| パスワードの照合を多数同時に送ったとき | 下の 2 | 問題なし |
| デプロイの途中で接続が切れたとき | 下の 3 | **不具合。#224 で直した** |
| 組み込み JS の時間の上限が、ホスト関数を待っている間も効くか | 下の 4 | 問題なし（テストを足した） |
| ヘッダーをゆっくり送る接続 | 下の 5 | 問題なし |
| 本文をゆっくり読む接続 | 下の 5 | 既存のテストで確認済み |

### 1. 検索を多数同時に送る

ワークスペース A の配信 API に、キーワード検索の登録済みクエリを 300 件同時に POST しました。その間、0.1秒おきに次の2つを測りました。
- ワークスペース B の配信 API（記事の一覧）
- 管理 API（`/api/admin/me`）

| | 平常時（中央値 / 最大） | 負荷の間（中央値 / 最大） |
|---|---|---|
| A の検索（300件） | — | 368ms / 525ms。すべて 200 |
| B の配信 | 6ms / 12ms | 22ms / 149ms。すべて 200 |
| 管理 API | 1ms / 3ms | 5ms / 53ms |

1つのワークスペースへの同時の検索で、ほかのワークスペースや管理 API が止まることはありませんでした。

### 2. パスワードの照合を多数同時に送る

存在しないアドレスへのログインを 60 件同時に送りました。照合のための Argon2 は、存在しないアドレスでも計算します。
- 28 件が 401 でした。残りの 32 件は、接続元ごとのログインの回数制限（毎分30回）で 429 になりました。
- 照合の最大は 604ms でした。
- その間の B の配信（最大 84ms）と管理 API（最大 9ms）は、止まりませんでした。

1つの接続元から同時に照合させられる数は、回数制限で抑えられています。多数の接続元からの照合は、この環境では確かめていません。

### 3. デプロイの途中で接続を切る

デプロイのリクエストを、送ってから数ミリ秒で切る操作を15回行いました（毎回フィールドを1つ足した新しい版）。
- 切らなかったデプロイは、すぐに通りました。
- **ただし、切った後も、移行用の接続（`yomi_migrate`）がデプロイのロック（アドバイザリーロック）を持ったまま待機していました（`pg_locks`）。**
- 移行用の接続は1本だけなので、次のデプロイは同じ接続で同じロックを取り直せます。そのため、詰まりませんでした。ただし、接続が入れ替わると、すべてのデプロイとワークスペースの作成が待ち続けます。

原因と直し方は #224 にあります。ロックを取ってから外すまでを、別のタスクで動かすようにしました。直す前のコードで失敗する結合テストも足しました。

### 4. 組み込み JS の時間の上限とホスト関数

`yomi.http.fetch` と `yomi.content.get` は、残り時間を上限にして相手を待ちます（`script/host.rs`）。動いている環境では遅い宛先を用意しにくいので、結合テスト `hook_time_limit` を足しました。テストは、リクエストを受けてから30秒待って応答する相手を手元に立て、時間の上限を1秒にした非同期のフックから送ります。フックは失敗し、5秒以内に戻ることを確かめました。

### 5. ゆっくり送る・ゆっくり読む接続

- ヘッダーをゆっくり送る: Caddy を通さずに CMS（`172.31.250.20:8080`）へ直接つなぎました。ヘッダーを5秒に1行ずつ送ったところ、30秒で CMS が接続を閉じました（#194 のヘッダーの読み取りの上限のとおり）。
- 本文をゆっくり読む: メディアの配信は、相手が次の分を受け取るまで30秒、1ファイル全体で10分を上限にしています。この上限は単体のテスト（`media/serve.rs`）で確かめています。この環境では別に試していません。Caddy を前に置く構成では、遅い相手を待つのは Caddy です。

## 確かめていないこと

- 多数の接続元からの負荷（分散した攻撃）と、長時間の負荷
- 本物の LLM での回答
- SSO（IdP を足す必要がある）の流れ
- 外部の侵入テストの範囲のその他の項目（攻撃者の視点での調査）
