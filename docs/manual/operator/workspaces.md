# ワークスペースと利用者

## テンプレートをデプロイする

ワークスペースを作る前に、テンプレートをデプロイします。デプロイはサーバー管理者だけができます。**デプロイの権限は、サーバーの上でコードを動かす権限と同じです。** テンプレートの中の関数を確かめてからデプロイしてください。

### 同梱の見本（blog）を管理画面からデプロイする

リリースには見本のテンプレート `blog`（リポジトリの `templates/blog`）が入っています。これだけは、CLI なしで管理画面からデプロイできます。

1. 「サーバーの管理」→「テンプレート」を開きます。
2. 「記事の公開URLのサイト」に、サイトのオリジン（`https://example.com` の形。パスは付けません）を入れます。見本の記事の URL（`https://example.com/ja/blog/<スラッグ>`）のサイトの部分を、これに置き換えてデプロイします。手元で試すときだけ `http://localhost:3000` のような http も使えます。
3. `blog` の「確認する」を押します。デプロイしたときの結果（破壊的な変更、壊れる登録済みのクエリ）が出ます。この時点では何も変わりません。
4. 問題がなければ「デプロイする」を押し、本人の確認（多要素認証のコード）をします。
5. ワークスペースを作るときに、テンプレートの名前に `blog` と入れます。すでに `blog` を使うワークスペースには、すぐに反映されます。

一覧には、デプロイ済みの版と、同梱の中身と同じか（サイトの部分を除いて比べます）が出ます。新しいリリースで見本が変わったら「同梱と違う」になるので、もう一度デプロイしてください。サイトの URL を変えてデプロイすると、記事の URL が変わり、変更の履歴とリダイレクトが残ります。

URL の形やフィールドを変えたいときは、`templates/blog` を元に自分のテンプレートを作り、CLI でデプロイします（下の手順）。

### 自分のテンプレートを CLI でデプロイする

1. 管理画面の「アカウント」→「個人トークン」で、権限「デプロイ」のトークンを発行します（本人の確認が求められます）。デプロイだけに使うトークンは、ワークスペースを選ばずに発行できます。
2. CLI でデプロイします（[テンプレートとCLI](../developer/templates-and-cli.md#デプロイ)）。

デプロイは監査ログに残ります。テンプレートを変えてデプロイすると、それを使うすべてのワークスペースに反映されます。移行に失敗したワークスペースは「移行待ち」になり、再試行します。ワークスペースの一覧で状態（「最新」「移行待ち」「スキーマ未適用」）を見られます。

## ワークスペースを作る

ワークスペースの一覧の「新しいワークスペース」で、名前とテンプレートを指定します。作成はサーバー管理者だけができます。

- テンプレートは、デプロイ済みのものから選びます。同梱の見本でまだデプロイしていないもの（`blog`）は、選べない形で出ます。先に上の手順でデプロイしてください。
- まだデプロイしていないテンプレートを使うときは「その他（名前を入力）」で名前を入れます（空なら `default`）。デプロイしたときに適用されます。

### テンプレートを後から切り替える

記事のあるワークスペースでも、テンプレートを別のデプロイ済みのテンプレートに切り替えられます。ワークスペースを開いて「管理」→「設定」の「テンプレートの切り替え」で行います（手順は[ワークスペースの管理者の章](../editor/workspace-admin.md#テンプレートの切り替え)）。

- 行えるのは、サーバー管理者と、重い権限「テンプレートの切り替え」を付与されたワークスペースの管理者だけです。**この権限を付与・取り消しできるのはサーバー管理者だけです**（ワークスペースを開いて「管理」→「所属者」）。
- 対応づけのないデータは消え、過去の版も新しい形に置き換わります。消えるデータは切り替えの前に JSON で書き出せます。
- 切り替えは監査ログに残り、管理者に通知されます。

続けて、そのワークスペースの管理者を招待します（「管理」→「招待」）。SMTP がなければ、招待のリンクはあなたの画面に一度だけ出るので、本人に渡してください。

## ワークスペースを削除する

ワークスペースを開いて「管理」→「設定」の「ワークスペースの削除」で行います。削除はサーバー管理者だけができます。

1. 確認のため、ワークスペースの名前をそのまま入力します。
2. 「ワークスペースを削除する」を押し、確認の画面で本人の確認（多要素認証のコード）をします。

- **すぐに完全に削除され、元に戻せません。** 記事・版・メディアのファイル・配信 API のキー・Webhook・所属・招待・設定と、ワークスペースの DB のスキーマとロールが消えます。配信もすぐに止まります。戻すにはバックアップから復旧します（[バックアップと復旧](backup.md)）。必要なら、削除の前にバックアップを取ってください。
- 利用者のアカウントは残ります（所属だけが外れます）。個人トークンからは、そのワークスペースが外れます。
- 監査ログの行は消えず、通常の保存期間まで残ります。削除の操作はインスタンス全体の監査ログに残り、管理者に通知されます。

## 上限

1つのワークスペースがインスタンスの資源を使い切らないよう、初めから有効な上限があります。「上限なし」にはできません。

| 上限 | 設定の場所 |
|---|---|
| 配信 API の回数 | [`[delivery]`](config.md#配信apidelivery) |
| 回答の回数 | [`[answer]`](config.md#回答apianswer) |
| メディアの大きさと容量 | [`[media]`](config.md#メディアmedia) |
| 組み込み JS のメモリと時間 | [`[scripts]`](config.md#組み込みjsscripts) |

これらの値はインスタンスで1つです。

## 予算の天井

ワークスペースの予算（訪問者向けの回答、編集者向けの支援、埋め込みの作成）の上限の上限です。LLM の料金はインスタンスのキーにかかるので、サーバー管理者が決めます。

- ワークスペースを開いて「予算」の「天井（サーバー管理者）」で、ワークスペースごとに決めます。「既定値」にすると、[設定ファイルの既定値](llm.md#予算の天井の既定値)（なければ 0）が効きます。
- 天井が 0 なら、そのワークスペースは LLM を呼びません。
- ワークスペースの管理者は、天井の範囲で上限を決めます。
- 変更は監査ログに残ります。

## 利用者

「サーバーの管理」→「利用者」に、全利用者の一覧があります。「パスワードのリセットを発行」「多要素認証のリセットを発行」で本人向けのリンクを発行できます。新しいパスワードを直接決める操作はありません。

### サーバー管理者の復旧

サーバー管理者は、ネットワーク越しには復旧できません。サーバーの上で実行します。どちらも、その人のセッションをすべて失効させます。

パスワードを決め直す（新しいパスワードは一度だけ表示されます）:

```bash
docker compose exec yomi yomi-server reset-password --config /data/config.toml --email you@example.com
```

多要素認証を解除する:

```bash
docker compose exec yomi yomi-server reset-mfa --config /data/config.toml --email you@example.com
```

どちらのコマンドも、その人のセッションと個人トークンをすべて失効させ、外部のアカウントのひも付けも消します（乗っ取られたときに、攻撃者が作ったものを残さないためです。SSO を使う人は、ログインし直してひも付け直してください）。

1人だけログインできないようにする（退職者や、乗っ取られた疑いのある人。セッションと個人トークンもすべて失効します）:

```bash
docker compose exec yomi yomi-server disable-user --config /data/config.toml --email someone@example.com
```

元に戻すときは `enable-user` です。

サーバー管理者は2人以上置くことを勧めます。追加も `create-server-admin` で行います。

## 全員への多要素認証の必須

既定で有効です（`[auth] mfa_required_for_everyone`）。無効にすると、管理者以外のロールは任意になります。**有効のままにすることを勧めます。** よく使われるパスワードの一覧は同梱していないので、漏えいしたパスワードへの備えは、これと [漏えいしたパスワードの照会](config.md#漏えいしたパスワードの照会authbreached_passwords) が担います。
