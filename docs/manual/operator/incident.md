# 事故対応

何かが漏れた、乗っ取られたと思ったときの手順です。**迷ったら、まず止めて、次に記録を残してください。**

## 最初にすること

1. **記録を残す**: いつ何に気づいたかをメモします。サーバーのログと監査ログを、消える前に写します。
2. **影響の範囲を考える**: 何が漏れたか（下の表）、どのワークスペースか、個人情報は含まれるか。
3. **止める・入れ替える**: 下の表のとおりに行います。
4. **知らせる**: [誰に知らせるか](#誰に知らせるか) を見ます。
5. **原因を直す**: 直るまでは公開を止めることも考えてください。脆弱性が疑われるなら `SECURITY.md` の窓口に報告してください。

## 何を入れ替えるか

| 漏れたかもしれないもの | すること |
|---|---|
| ある人のアカウント | その人のリセットを発行し、セッションを終了させます。[サーバー管理者なら CLI で](workspaces.md#サーバー管理者の復旧) |
| 1つの配信APIのキー | 管理の「配信APIのキー」で失効させて発行し直します |
| 多くの配信APIのキー | [すべて入れ替えます](#すべての配信apiのキーを入れ替える) |
| セッションや個人トークン | [すべて失効させます](#すべてのセッションと個人トークンを失効させる) |
| Webhook の署名の秘密 | 管理の「Webhook」の「秘密を入れ替える」（24時間は古い秘密でも署名されます。急ぐときは Webhook を削除して登録し直します） |
| ワークスペースの LLM の API キー | 提供会社の側で失効させ、「LLMの接続設定」で新しいキーを入れます |
| 設定ファイル（DB のパスワード、`[llm]` のキー、SMTP のパスワードなど） | それぞれの値を入れ替えて再起動します。DB のパスワードは下の手順で |
| 暗号化の鍵 | [鍵を入れ替えます](#暗号化の鍵を入れ替える)。**それで暗号化していた秘密（LLM のキー、Webhook の秘密など）も漏れたものとして入れ替えてください** |
| DB のバックアップ | 利用者のパスワードはハッシュですが、記事や質問ログは読めます。個人情報の扱いを考えます |
| サーバーそのもの | 別のサーバーを作り、確かなバックアップから復旧し、**上のすべて**を入れ替えます |

## 緊急停止のコマンド

サーバーの上でだけ実行できます。ネットワーク越しの管理 API からはできません。実行は監査ログに残ります。

### すべてのセッションと個人トークンを失効させる

次のものをすべて失効させます。全員がログインし直しになり、未承諾の招待は送り直しになります。

- セッション（多要素認証の途中のものを含む）と個人トークン
- 使っていないパスワードと多要素認証のリセットのリンク
- 未承諾の招待
- すべてのワークスペースのプレビュー用のリンク

```bash
docker compose exec yomi yomi-server revoke-all-sessions --config /data/config.toml --yes
```

### すべての配信APIのキーを入れ替える

古い値はすぐに使えなくなります。新しい値は一度だけ、1行に1つ（ワークスペースID、キーID、名前、新しいキー。タブ区切り）表示されます。**サイトの設定を入れ替えるまで、サイトは配信 API を読めません。** `--workspace <ID>` で1つのワークスペースに絞れます。

```bash
docker compose exec yomi yomi-server rotate-api-keys --config /data/config.toml --yes
```

### 暗号化の鍵を入れ替える

1. 鍵のファイルに新しい版の鍵を足します。

   ```bash
   docker compose exec yomi yomi-server add-encryption-key --config /data/config.toml
   ```

2. サーバーを再起動します。新しい秘密は新しい鍵で暗号化されます。

   ```bash
   docker compose restart yomi
   ```

3. 保存済みの秘密を暗号化し直します。使っている鍵の版が表示されます。何度実行してもかまいません。

   ```bash
   docker compose exec yomi yomi-server reencrypt-secrets --config /data/config.toml --yes
   ```

4. 古い版の鍵を外して、再起動します。古い版を使う値が残っていれば断られます。

   ```bash
   docker compose exec yomi yomi-server remove-encryption-key --config /data/config.toml --version 1 --yes
   ```

   ```bash
   docker compose restart yomi
   ```

5. **新しい鍵のファイルを、バックアップの保管先に入れ替えます**（[バックアップと復旧](backup.md)）。

途中だった SSO のログインはやり直しになります。

### DB のパスワードを入れ替える

1. DB の側で変えます。

   ```bash
   docker compose exec db psql -U postgres -c "ALTER ROLE yomi_app PASSWORD '<新しい値>'"
   ```

   ```bash
   docker compose exec db psql -U postgres -c "ALTER ROLE yomi_migrate PASSWORD '<新しい値>'"
   ```

2. `config.toml` の `[database]` と `[migration_database]` の `password` を同じ値に変えて、再起動します。

値は16文字以上のランダムなものにしてください。シェルの履歴に残るので、後で消してください。

## 調べる

- 監査ログ（「サーバーの管理」→「監査ログ」と、書き出した先）で、いつ誰が何をしたかを見ます。
- 利用者ごとのログインの履歴（IP アドレス、ブラウザ、国）は90日分あります。
- 急増の通知に、件数の多い IP アドレスとアカウントが出ます。

## 誰に知らせるか

- **影響を受ける利用者と、ワークスペースの管理者**: 何が起き、相手に何をしてほしいか（パスワードの変更など）を伝えます。
- **サイトの訪問者**: 質問ログや個人情報が関わるとき。
- **脆弱性が疑われるとき**: `SECURITY.md` の窓口。

### 個人情報保護法について（日本）

日本の個人情報保護法では、一定の個人データの漏えいなどについて、**個人情報保護委員会への報告と、本人への通知が義務**になっています。要配慮個人情報が含まれるとき、財産的な被害のおそれがあるとき、不正の目的によるおそれがあるとき、本人の数が1,000人を超えるときなどです。報告には期限があります（速報は発覚からおおむね3〜5日以内、確報は原則30日以内。不正の目的によるおそれがあるときは60日以内）。

**CMS を運用する事業者の責任です。** 最新の要件は個人情報保護委員会の案内で確かめ、必要なら専門家に相談してください。日本以外の訪問者や利用者がいるなら、その国の法律も確かめてください。

CMS に個人情報が入りうる場所は、利用者のアカウント（メールアドレス、表示名）、ログインの履歴（IP アドレス、ブラウザ、国）、質問ログ（伏せられない自由な書き方）、記事の本文とメディアです。

## 普段から備えておくこと

- [バックアップ](backup.md) と復旧の練習。暗号化の鍵を別の場所に。
- サーバー管理者を2人以上。復旧コードの保管。
- [監査ログの書き出し](monitoring.md#監査ログの書き出し) と通知の受け取り先。
- この手順を印刷するか、サーバーの外に置く。
- 誰が判断し、誰に連絡するかを決めておく。
