# コードの品質と作業の流れ

CLAUDE.md の禁止事項・設計の原則・約束のテストが常に優先する。このスキルは、その上でのコードの書き方と進め方を決める。

## 判断の優先順位

観点がぶつかったら、この順で優先する。

1. **正しさ**（約束のテストが通る、エッジケースとエラーを扱う、パニックしない）
2. **読みやすさ**（人間にもAIにも、後から読んで意図がわかる）
3. **開発の効率**（手戻りが少ない、既存の部品を使い回す）
4. **実行の効率**（速さ、メモリ、DBへの問い合わせの回数）

例外: 計測でボトルネックとわかった箇所に限り、実行の効率を読みやすさより優先してよい。そのときは、計測の結果と理由をコメントに残す。計測せずに推測で最適化しない。

## 人間にもAIにも読みやすいコード

- **小さく保つ。** 新しく書く関数は40行、ファイルは300行を目安にする。既に超えているファイルに書き足すときは、足す部分を別の関数やファイルに分けられないか考える。大きな分割は、別の変更として提案する。
- **型を明示する。** TypeScript で `any`、型の断定（`as`）での逃げ、暗黙の変換を使わない。Rust で意味の違う値（ID、トークン数など）を同じ素の型で混ぜない。
- **コメントは「なぜ」を書く。** 何をしているかはコードで伝える。決定の根拠があれば、既存のコードと同じく `docs/decisions/` のファイル名や Q番号を書く。
- **名前を省略しない。** 同じ概念には、リポジトリの中で既に使われている同じ名前を使う。新しい名前を作る前に、既存の名前を探す。
- **マジックナンバーと隠れた副作用を作らない。** 上限や時間は名前付きの定数にする。関数の名前から想像できない書き込みや通信をしない。
- **テストは仕様書として読めるようにする。** 何を約束しているかがテストの名前と説明でわかるようにする。
- **既存の書き方に合わせる。** 新しい書き方を持ち込む前に、同じことをしている既存のコードを探して合わせる。

言語ごとの決まりは、`rust-server`（`server/`）と `admin-nuxt`（`admin/`）のスキルを読む。

## 作業の流れ（毎回すべて行う）

### 1. 計画

- CLAUDE.md の「作業の進め方」に従い、関係する `docs/decisions/` と約束を確認する。
- 変更するファイル、使い回す既存の部品、追加・変更するテストを短く書き出す。
- 「人間のレビューが必須の領域」に触れるかどうかを判定する。触れるなら、その変更だけを独立させる。

### 2. 実装

- 新しい依存は追加しない。必要なら、CLAUDE.md の「依存ライブラリ」の手順で承認を求める。
- ファイルの編集後の整形は hooks が自動で行う（Rust は `rustfmt`、管理画面は `eslint --fix`）。

### 3. テストとチェック

変更した範囲に応じて、次を実行してすべて通す。失敗したら実装を直す。テストを緩めない。

| 範囲 | コマンド |
|---|---|
| `server/` | `scripts/cargo.sh fmt --check` / `scripts/cargo.sh clippy --locked --all-targets -- -D warnings` / `scripts/cargo-db-test.sh`（DB のテストを含む） |
| `admin/` | `npm run lint -w @yomotsuhirasaka/admin` / `npm run typecheck -w @yomotsuhirasaka/admin` / `npm run generate -w @yomotsuhirasaka/admin` |
| `cli/` | `npm test -w @yomotsuhirasaka/cli`（ビルドと単体テスト） |
| `packages/*`、`tools/mock-llm/` | `npm run typecheck -w <パッケージ名>` / `npm test -w <パッケージ名>`（`build` があるものは `npm run build` も） |
| 同梱のテンプレート | `node scripts/check-bundled-templates.mjs` |
| `tests/invariants/` | `tests/invariants/` で `npm run typecheck` |
| 約束 | 関係する `tests/invariants/` のテスト（環境は `tests/invariants/README.md`） |

CI（`.github/workflows/ci.yml`）が同じチェックを流す。迷ったら CI の手順に合わせる。

環境の都合で実行できなかったテストがあれば、黙って飛ばさず、何が実行できなかったかを報告する。

### 4. レビュー

テストが通ったあとに、次の順で行う。

1. `/simplify` — 重複、冗長さ、既存の部品の使い回しを整理する
2. `/code-review medium` — バグを探す
3. 変更が CLAUDE.md の「人間のレビューが必須の領域」に触れるときは、`/security-review` も行う

レビューでコードを直したら、3 のテストとチェックをもう一度通す。レビューのあとに実装を変えたとき（速さの改善を足したなど）は、変えた部分について 1〜3 のレビューもやり直してから PR にする。最後に、利用者へ変更の内容、理由、確認したこと、確認できなかったことを報告する。
